# Inbound mail — webhook, ingestion, threading, attachments

## Inbound webhook (Resend / Svix)

- `src/lib/server/webhooks/svix.ts` (US-E01) is the **only** place a webhook signature is verified: `verifySvixRequest(request)` reads `svix-id`/`svix-timestamp`/`svix-signature`, reads the body as **text**, and returns `{ ok: true, payload, rawBody } | { ok: false, reason }`. Three things to preserve:
  - It consumes the request body itself, as raw text. The Svix signature covers the exact bytes Resend sent, so `request.json()` followed by a re-serialize will not verify. A `Request` body can only be read once — callers must use the returned `payload`/`rawBody` and never call `request.json()` before or after.
  - `payload` exists only on the `ok: true` branch by construction, so US-E02..E05's ingestion code physically cannot reach an unverified body. Keep the result type discriminated rather than returning a payload plus a boolean.
  - `reason` is for `console.warn` server-side only. The endpoint returns a bare `401` with no detail — a failure reason tells an unauthenticated caller how to forge a better signature.
- The `RESEND_INBOUND_WEBHOOK_SECRET` read is **lazy** (memoized `Webhook` on first verify), not import-time, for the same reason as `email/resend.ts`: `npm run build` imports every `+server.ts` during method detection, so an import-time secret check would make the build require a real credential.
- `POST /api/webhooks/resend-inbound` (`src/routes/api/webhooks/resend-inbound/+server.ts`) is the gate; US-E02 onward hangs parsing/persistence off the verified `result.payload` inside it, and must not add a second parallel verification path.
- `src/lib/server/webhooks/verify-inbound-webhook.mts` smoke-tests the endpoint over HTTP against a running dev server (`WEBHOOK_BASE_URL`, default `http://localhost:5173`), using `svix`'s own `sign()` for the positive case. US-E02/E03 extended it to 14 checks by adding the full ingestion path against a real received email (see below), including the two status-code-contract cases: a non-`email.received` event and a permanently-unfetchable `email_id` both answered with `200`, not `500`. The load-bearing signature case is **tampered body + genuine signature → 401**: that's what proves the raw bytes are what's verified. Extend this script rather than adding new ad hoc webhook scripts.
- **Deployed and live** as of US-E01: the app is served from `https://mail.caseynazelrod.com` (Vercel, builds from `main`), the webhook is registered in the Resend dashboard against `POST https://mail.caseynazelrod.com/api/webhooks/resend-inbound`, and the real `whsec_…` secret is in both the local `.env` and Vercel project settings. Re-run the suite against production with `WEBHOOK_BASE_URL=https://mail.caseynazelrod.com node --env-file=.env node_modules/.bin/tsx src/lib/server/webhooks/verify-inbound-webhook.mts` (5/5 signature cases as of the US-E01 merge; 14/14 including the US-E02/E03 ingestion cases locally).
- DNS split worth knowing before touching domains: Resend owns `send.` (sending), `links.` (click tracking), and the **apex MX** (receiving); the app has the `mail.` subdomain to itself. So **inbound addresses are on the apex** — `something@caseynazelrod.com`, never `@mail.caseynazelrod.com`. Don't move the app onto a name that also holds MX records: Vercel wants a CNAME for a subdomain, and a CNAME must be the only record at its name, so it would block the MX outright (use an A record if that's ever unavoidable).
- Still unconfirmed as of US-E02: nothing has yet proven that a **real Resend delivery** reaches the deployed endpoint and passes `svix` verification. Apex MX receiving works (real inbound emails exist in the Resend account, and US-E02's parser was built against one), and the whole ingestion path is proven end-to-end locally against a real received email — but the signature leg is still this repo's own `sign()` hitting its own endpoint. Confirming it needs a real email plus a `200` for `/api/webhooks/resend-inbound` in the Vercel function logs.

## Inbound ingestion (parse + contacts)

- **The `email.received` webhook payload is metadata-only** — no body, no headers, no attachment content ("This design choice supports large attachments in serverless environments that have limited request body sizes"). This was confirmed against the real Resend account in US-E02 and it shapes all of US-E02..E05: `html`/`text`, the `From:` display name, `In-Reply-To`, `References` and the `Date:` header exist **only** on the fetched record. Ingestion is inherently two calls — verify the webhook, then `fetchReceivedEmail(email_id)` (`src/lib/server/email/resend.ts`, wrapping `resend.emails.receiving.get`). Attachment _content_ likewise needs the Attachments API (US-E05), not a base64 blob in the request body.
- Two quirks of the real fetched record, both pinned by fixtures in `verify-inbound-parse.mts`: Resend hands some header values back **JSON-encoded** (an observed delivery had `date: "\"2026-07-25T15:15:31.000Z\""`, `received: "[\"from …\"]"`), and header keys are lowercased. `headerValues()` in `parse.ts` decodes both encodings — a `"`-prefixed value to a single string, a `[`-prefixed one to a list (that's how a header occurring more than once comes back) — and falls back to the raw text when `JSON.parse` throws, so a display name like `"Google" <a@b>` survives untouched. `header()` is the single-value view (first entry). Multi-value headers must read `headerValues`, not `header`: `References` whitespace-split from an undecoded `["<id>"]` string would silently feed JSON punctuation into US-E04's threading.
- `parse.ts`'s `inboundMessageId` guarantees `ParsedInboundEmail.messageId` is **never empty** — an absent, null or blank `message_id` falls back to `<resend-{received.id}@inbound.invalid>`. `Message-ID` is optional in RFC 5322 and Resend does not validate it, and it is this app's idempotence key: an empty string would make `getEmailByMessageId('')` match the first such email and then silently drop every later one as a duplicate (mail lost behind a `200` — the worst failure this pipeline has), while a null would fail the `NOT NULL` insert and 500 forever against a permanent condition. The fallback uses Resend's own email id because it is unique per received email and stable across redeliveries, so idempotence still holds where it matters. Don't reintroduce a bare `received.message_id` read.
- The bare sender address is read from the record's own `from` field, **never** from `headers.from` — the header is only mined for the display name. A crafted `From:` must not be able to disagree with the envelope Resend actually validated. Keep that split if `parse.ts` grows.
- `src/lib/server/inbound/parse.ts` is pure by design (no env, no db, no network) so a standalone `tsx` script can exercise it against captured fixtures. Keep new parsing logic there rather than inside the `+server.ts`, and keep the fixture-based script (`src/lib/server/inbound/verify-inbound-parse.mts`) as the place US-E03/E04/E05 add parsing assertions.
- Endpoint status-code contract, worth preserving: **permanent** conditions return `200` with a server-side `console.warn` — a verified but unusable payload (wrong event type, missing `email_id`), _and_ a Received-emails fetch that fails with a 4xx (an `email_id` that is gone or inaccessible). Resend retries 5xx forever and none of those can start working. Only a **transient** failure (a 5xx/429/transport error from Resend, or the DB) is allowed to throw → `500`, which is exactly when a retry helps. `fetchReceivedEmail` encodes that split for the caller: it throws a `ReceivedEmailFetchError` carrying `retryable` (derived from `error.statusCode`) rather than a bare `Error`, so the endpoint doesn't have to re-classify provider errors itself. Getting this backwards either drops mail silently or builds an infinite retry loop.
- The endpoint's success `console.log` deliberately **omits the sender's email address** — it would write a real person's address into the platform's function logs on every delivery, and the `contact` id already identifies the row. Keep new inbound log lines id-only.
- `src/lib/server/inbound/sanitize.ts` (US-E03) is the **only** place inbound HTML is sanitized, and it runs on the **write** path: `sanitizeEmailHtml` is called by `storeInboundEmail` so what lands in `emails.body_html` is already safe and no renderer downstream can forget to re-sanitize. Never persist Resend's raw `html`. It's `isomorphic-dompurify` with an explicit `FORBID_TAGS`/`FORBID_ATTR` list on top of the defaults (`iframe`/`link`/`style`/`form`/`svg`…, plus `srcset`/`background`/`ping`/`style`/`formaction`) — DOMPurify already strips `script` and every `on*` handler, but a default is a thing that can change under us and a mail client leaking a read receipt via `<iframe>`/`<link>` is exactly the threat here. A blank or entirely-malicious body sanitizes to `null`, not `''`, so the column stays NULL. `body_text` is stored verbatim: it is never rendered as markup.
- `src/lib/server/inbound/store.ts`'s `storeInboundEmail` is the persistence step (parse → sanitize → insert), and `src/lib/server/db/emails.ts` holds the `emails`/`threads` query helpers (db-handle-first, same as `contacts.ts`). Idempotence on `message_id` (FR-2) is enforced **twice on purpose**: a cheap `getEmailByMessageId` read up front so a redelivery never creates an orphan `threads` row, and `insertInboundEmail`'s `onConflictDoNothing()` + re-read as the authority underneath for two genuinely concurrent deliveries. Only the index can win that race; only the read can avoid the litter — and when the read misses but the index catches it, the thread just created is deleted again. US-E04 replaces the _choice_ of thread inside `storeInboundEmail` (In-Reply-To / subject matching) but not this structure.
- Thread assignment, the email insert and the thread touch run inside **one `db.transaction`**. This is load-bearing in both directions and must not be unwound into sequential calls: a failure _after_ the insert would leave a stored email whose thread still reads as read with a stale `last_message_at`, and because the up-front duplicate check short-circuits, Resend's redelivery returns early and never repairs it — the message is stranded out of the inbox sort order permanently. Rolling back also means a failed insert takes its just-created thread with it, so no best-effort cleanup path can get it wrong. Because the thread row is still uncommitted, the duplicate branch's `deleteThread` also can't hit an FK violation from a concurrent delivery attaching to it. `Database` in `src/lib/server/db/types.ts` is therefore a **union of the singleton and a transaction handle**, which is what lets every query helper run unchanged on either.
- `src/lib/server/db/contacts.ts` owns the `contacts` table (db-handle-first, same pattern as the auth helpers). Three invariants: addresses are stored **lowercased** (`normalizeEmail`) because `contacts_email_unique` is a plain case-sensitive SQLite index and that normalization is what makes it enforce one row per address, while reads still compare with `lower()`; the insert uses `onConflictDoNothing()` + a re-read so a concurrent redelivery of the same email is a no-op rather than a 500; and a contact with `auto_created = false` has been **hand-edited by the owner** (US-I02) so its name is never overwritten by an inbound display name. An `auto_created = true` contact does get its name refreshed, since a later delivery carrying a display name beats the null a bare-address delivery left behind.

### Threading (US-E04)

- `src/lib/server/inbound/threading.ts` owns `normalizeSubject` (strips stacked `Re:`/`Fwd:`/`Aw:`/`Sv:`… prefixes, including `Re[2]:`, collapses whitespace, lowercases) and `SUBJECT_THREAD_WINDOW_MS` (30 days, FR-4). Pure, like `parse.ts`.
- **`threads.subject` stores the normalized subject; `emails.subject` keeps the sender's original wording.** The normalized column is the grouping key for the subject fallback, so writing a raw `Re: …` into it would silently stop that thread from ever matching again. Anything rendering a thread header (US-F01/G01) should expect a lowercased, prefix-stripped string and may prefer the newest email's own subject.
- `assignThread` in `inbound/store.ts` is the single place a thread is chosen, in this order: `In-Reply-To`, then the `References` chain **nearest-ancestor-first** (so a reply whose direct parent this mailbox never received still threads), then the 30-day same-normalized-subject fallback, then a new thread. Headers beat the heuristic; never reorder that.
- Never let an **empty** normalized subject match the fallback — every subject-less email in the mailbox would collapse into one thread. `findThreadBySubject` returns early on `''`.
- Per the Data Model PRD, `threads.is_read` means "every message in the thread is read", so `touchThreadForNewMessage` forces it back to `false` on arrival, and `last_message_at` **only moves forward** — a late redelivery of an older message must not drag a thread down the inbox sort order. That comparison is a SQL `max()` inside the `UPDATE`, not a JS read-modify-write (same reason as `incrementAuthCodeAttempts`): two messages landing in one thread concurrently would otherwise interleave select-then-update and let the older timestamp win.
- `storeInboundEmail` takes an injectable `now` (default `new Date()`) purely so the 30-day window is testable, and returns `threadMatch: 'reply' | 'subject' | 'new' | 'duplicate'` for the endpoint's log line. A thread the call _created_ is deleted again if the email turns out to be a duplicate; a thread it merely _joined_ is left alone.

### Attachments (US-E05)

- `src/lib/server/inbound/attachments.ts` owns inbound attachment extraction; `src/lib/server/db/attachments.ts` is the `attachments` table's query helper (db-handle-first, like `emails.ts`). Attachment bytes are never written to a DB column (FR-5) — only `r2_object_key`.
- The two provider hops (`fetchReceivedAttachmentBytes` in `email/resend.ts`, `uploadToR2`) are **injected** into `storeInboundAttachments` as a `deps` object rather than imported, because both of those modules read env — that's what keeps this module runnable from the standalone `tsx` verification script with stubs, same as `parse.ts`/`store.ts`. The endpoint wires the real implementations.
- Resend's Attachments API returns a short-lived signed `download_url`, not the bytes; `fetchReceivedAttachmentBytes` does both hops and deliberately never returns or persists that URL — it expires, and the app's own download links are presigned from R2 on demand.
- If the upload succeeds but the `attachments` insert then fails, the just-uploaded object is deleted again via the optional `remove` dep (`deleteFromR2`): nothing would reference it and the email's duplicate check means no redelivery ever repairs it, so without the undo the bucket accumulates unreachable blobs. A failure of the delete itself is only logged.
- Per-attachment failures are **swallowed and logged**, never thrown: the email row is already committed and acknowledged, so a throw would make Resend redeliver a message whose duplicate check short-circuits — the retry couldn't repair the attachment and every attempt would be a 500 no-op. A retry-later state is out of scope for v1.
- Attachments are processed **sequentially** (bounded peak memory in a serverless function), only when `storeInboundEmail` reports `created` (a redelivery's bytes are already in R2 under the same key), and `size_bytes` comes from the downloaded bytes rather than the reported metadata size (metadata can describe the transfer-encoded size).
- The R2 key is `inbound/<resend_email_id>/<attachment_id>[-<slugified filename>]`. Resend's attachment id — not the filename — is what makes it unique: two attachments on one email can share a name, and a sender-supplied string must never decide where an object lands. `attachmentFilename` reduces a nullable, sender-controlled filename to one path segment (no traversal), strips control bytes, and falls back to `attachment-<id>`.
- Cleanup order in any script that deletes inbound rows: **attachments → emails → threads**. The remote Turso connection enforces the `attachments.email_id` FK, so deleting emails first throws `SQLITE_CONSTRAINT`.
