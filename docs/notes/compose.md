# Compose — the recipient rule, the field, and the action's shape

Covers US-H01 (`/compose`, the screen and the send gate). US-H02–H05 add the send, reply/forward pre-fill and attachments on top of this; read this before touching any of them.

## `src/lib/compose/addresses.ts` is the single definition of "sendable"

- Pure (no env, no db, no DOM), like `lib/inbox/format.ts`, and for a sharper reason: **the browser gates the Send button and the server action re-checks the submitted form with the same `validateComposeDraft`.** If a second rule ever appears on either side they will drift, and the drift is silent — the owner sees an enabled button and the server refuses, or worse the reverse. Add recipient/validation logic here, not in the page and not in the action.
- The rule: at least one valid To address, **and** a non-empty subject **or** a non-empty body (whitespace doesn't count). A malformed **Cc** also blocks the send even though Cc is optional — a typo'd Cc is a recipient who silently never receives the mail. An _empty_ Cc is fine; that's what makes it optional.
- **Separators are found by a scan that ignores quotes and angle brackets** (`separatorIndices`), not by `String.split(/[,;]/)`. `"Doe, Jane" <jane@x.com>` is the most common shape a copy-paste out of another mail client produces, and splitting on its comma left `"Doe` behind as a permanently invalid entry that disabled Send with no way out but retyping. The splitter and the caret helpers share that one scan.
- `validateComposeDraft` also **returns the parsed `to`/`cc` arrays**, so the send path in US-H02 uses the exact list that was validated instead of parsing a second time, and it rejects an address that appears in **both** To and Cc (per-field de-duplication would otherwise let one person be delivered to twice).
- `parseAddressList` lowercases and de-duplicates, matching how `contacts.email` is stored (`normalizeEmail` in `server/db/contacts.ts`), splits on `,` **and** `;`, accepts the `Name <addr@x.com>` paste form (dropping the display name), and reports non-empty junk in `invalid` while silently ignoring empty entries — a trailing comma is how you type the _next_ address, not an error.
- Address syntax is a deliberate conservative subset, not RFC 5322. The pattern is anchored and has no quantified group that can match the same text two ways: a pasted recipient list is untrusted input, and `lib/inbox/format.ts`'s `HTML_TAG` comment records what a backtracking pattern cost this app once already.
- `activeEntry` / `replaceActiveEntry` / `suggestContacts` are the autocomplete's logic, kept here rather than in the component so they're assertable without a browser. `replaceActiveEntry` must shed the separator at `entry.end` (the one it writes is the one that belongs there) or picking a contact mid-list leaves an empty `, ,` behind — that was a real bug, caught by the verify script.
- `src/lib/compose/verify-compose-addresses.mts` is this area's standalone check (`npx tsx src/lib/compose/verify-compose-addresses.mts`, 41 checks, no db/env). **Extend it** rather than adding a new script, per the repo convention. It imports `./addresses.ts` by relative path because bare `tsx` has no Vite alias resolution.

## The recipient field

- `RecipientField.svelte` is **one plain `<input name="to">` holding a comma-separated list**, not a chip/token widget over a hidden input. The value that submits is the value the owner can see and edit (a hidden mirror is a second source of truth that can disagree with the chips), and the field works with no JavaScript — the suggestion popup is the only scripted part and it is purely additive.
- The popup is a hand-rolled ARIA combobox, not a `<datalist>`: `<datalist>` can't be themed to the Dusk Terminal surface, matches on the _whole_ field value (so it stops suggesting once the field holds a first address plus a fragment), and isn't reliably driveable from rodney.
- The caret position is mirrored into state on purpose. Which entry is "being typed" is a function of the caret, not of the value, so clicking back into an earlier address has to re-target the suggestions. After choosing a contact the caret is restored in a `requestAnimationFrame` — before Svelte has flushed the new value, `setSelectionRange` lands in the wrong place.
- **Hover does not set the keyboard's active option**, and **Tab does not take the highlighted suggestion**. With hover driving `activeIndex`, the popup opens right where the pointer already is, so Enter took a contact the reader never navigated to and `aria-activedescendant` announced it; and stealing Tab meant the only way out of the To field was dismissing a popup the reader may not know is open. Hover is `hover:bg-background` styling only.
- **`onfocus` does not open the popup.** Tabbing into a field selects its whole value, putting `selectionStart` at 0, so the popup would open against the _first_ address in the list. Typing or clicking opens it.
- The popup uses a border and the `surface`/`background` contrast, **never a drop shadow** (`tasks/prd-ui-ux.md`'s Shape & Depth rule; `grep shadow src/` should stay empty).
- An option's `onmousedown` calls `preventDefault()`. Without it, the input's `blur` closes the popup before the click that is choosing an option ever lands.
- Both the combobox input and the `+ Cc` button carry `aria-expanded`, so **`button[aria-expanded=false]` is not a unique selector** — the `+ Cc` toggle has `id="cc-toggle"` and the compose form has `id="compose-form"` (the shell's logout form is the first `form` in the document) precisely so a browser check can address them. Keep those ids.
- When the To popup is open it is absolutely positioned **over** the `+ Cc` button, so a click there hits the suggestion. Move focus off the field first (that's what the demo does) — this is real behaviour, not a test artifact.

## The page and the action

- Cc collapsed means **not rendered**, so the form submits no `cc` field; the action reads a missing field as `''`, the same as an empty one. Nothing hidden holds a stale value. It opens itself when a returned draft has a Cc, so a rejected submit can't hide typed addresses behind a closed toggle.
- **The Send button is `disabled` only in the browser** (`browser && !validation.valid`). An unconditional `disabled` is server-rendered against the empty draft, so a client with no JavaScript gets a button it can never re-enable and the action — the real enforcement — becomes unreachable. Don't drop the `browser` guard.
- Validation _messages_ are gated on a per-field `touched` flag (one delegated `oninput` handler on the form, keyed off the input's `name`); the _button_ is gated on validity alone. Marking every field touched on any keystroke made typing the first character of an address pop up a complaint about the missing subject — don't go back to that.
- **The `send` action validates the session itself.** It mutates nothing in US-H01, but SvelteKit runs an action _before_ any `load`, so `(app)/+layout.server.ts` cannot protect it, and US-H02 turns this body into a real send. The check is built in now so that story can't forget it. Same trap as US-G03's `+server.ts` and US-G04's delete — see `docs/notes/auth.md` and the cross-cutting rule in `CLAUDE.md`.
- **Every return path echoes the draft back** (`ComposeResult` in `+page.server.ts` keeps success and failure structurally identical, so the page can read `form?.errors` off the `ActionData` union without narrowing). That is US-H02's FR-4 arriving early: the page seeds its field state from `form?.draft`, so a failed send re-renders what was typed. Keep new outcomes in that one shape.
- The page seeds `$state` from `form?.draft` inside `untrack(...)`: a deliberate one-time seed, not a binding — once the owner is typing, the field is the source of truth. The form is a plain (non-`enhance`d) POST, so every result arrives with a fresh mount.
- `+ Cc`'s and Send's styling: Send uses the accent, per the compose PRD's design note; a discard/remove affordance (US-H05) should use `text-danger`. Validation messages and other prose are **sans** (`font-sans text-sm`, matching `ErrorMessage.svelte`); only addresses, labels and the like are monospace — a subject is prose, so the Subject input is sans too. Any control that sets `focus-visible:outline-none` must add a visible substitute (`focus-visible:border-*`), as every other control in this app does.

## Entry point and demo data

- The **Compose link lives in the `(app)` shell's top bar**, unlike the search box and the thread list, which were deliberately pushed down into the inbox subtree. Writing a new message is not part of the inbox list's state, so every `(app)` route should offer it from the same place.
- `seed-f03-demo.mts` now also seeds three contacts on the throwaway `@f03-demo.example` domain (two with names sharing a fragment, one with no name) and removes them in `--cleanup` by that address pattern — never by anything that could match a real correspondent. Reuse them for compose demos instead of seeding contacts by hand.
