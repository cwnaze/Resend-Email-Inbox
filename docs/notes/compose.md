# Compose — the recipient rule, the field, and the action's shape

Covers US-H01 (`/compose`, the screen and the send gate). US-H02–H05 add the send, reply/forward pre-fill and attachments on top of this; read this before touching any of them.

## `src/lib/compose/addresses.ts` is the single definition of "sendable"

- Pure (no env, no db, no DOM), like `lib/inbox/format.ts`, and for a sharper reason: **the browser gates the Send button and the server action re-checks the submitted form with the same `validateComposeDraft`.** If a second rule ever appears on either side they will drift, and the drift is silent — the owner sees an enabled button and the server refuses, or worse the reverse. Add recipient/validation logic here, not in the page and not in the action.
- The rule: at least one valid To address, **and** a non-empty subject **or** a non-empty body (whitespace doesn't count). A malformed **Cc** also blocks the send even though Cc is optional — a typo'd Cc is a recipient who silently never receives the mail. An _empty_ Cc is fine; that's what makes it optional.
- **Separators are found by a scan that ignores quotes and angle brackets** (`separatorIndices`), not by `String.split(/[,;]/)`. `"Doe, Jane" <jane@x.com>` is the most common shape a copy-paste out of another mail client produces, and splitting on its comma left `"Doe` behind as a permanently invalid entry that disabled Send with no way out but retyping. The splitter and the caret helpers share that one scan.
- `validateComposeDraft` also **returns the parsed `to`/`cc` arrays**, so the send path in US-H02 uses the exact list that was validated instead of parsing a second time, and it rejects an address that appears in **both** To and Cc (per-field de-duplication would otherwise let one person be delivered to twice).
- `parseAddressList` lowercases and de-duplicates, matching how `contacts.email` is stored (`normalizeEmail` in `server/db/contacts.ts`), splits on `,` **and** `;`, accepts the `Name <addr@x.com>` paste form (dropping the display name), and reports non-empty junk in `invalid` while silently ignoring empty entries — a trailing comma is how you type the _next_ address, not an error.
- Address syntax is a deliberate conservative subset, not RFC 5322. The pattern is anchored and has no quantified group that can match the same text two ways: a pasted recipient list is untrusted input, and `lib/inbox/format.ts`'s `HTML_TAG` comment records what a backtracking pattern cost this app once already.
- `activeEntry` / `replaceActiveEntry` / `suggestContacts` are the autocomplete's logic, kept here rather than in the component so they're assertable without a browser. `replaceActiveEntry` must shed the separator at `entry.end` (the one it writes is the one that belongs there) or picking a contact mid-list leaves an empty `, ,` behind — that was a real bug, caught by the verify script.
- `src/lib/compose/verify-compose-addresses.mts` is this area's standalone check (`npx tsx src/lib/compose/verify-compose-addresses.mts`, 41 checks, no db/env). **Extend it** rather than adding a new script, per the repo convention. It imports `./addresses.ts` by relative path because bare `tsx` has no Vite alias resolution.

## The recipient field

- `RecipientField.svelte` is **one plain `<input name="to">` holding a comma-separated list**, not a chip/token widget over a hidden input. The value that submits is the value the owner can see and edit (a hidden mirror is a second source of truth that can disagree with the chips), and the field works with no JavaScript — the suggestion popup is the only scripted part and it is purely additive.
- The popup is a hand-rolled ARIA combobox, not a `<datalist>`: `<datalist>` can't be themed to the Dusk Terminal surface, matches on the _whole_ field value (so it stops suggesting once the field holds a first address plus a fragment), and isn't reliably driveable from rodney.
- The caret position is mirrored into state on purpose. Which entry is "being typed" is a function of the caret, not of the value, so clicking back into an earlier address has to re-target the suggestions. After choosing a contact the caret is restored in a `requestAnimationFrame` — before Svelte has flushed the new value, `setSelectionRange` lands in the wrong place.
- **Hover does not set the keyboard's active option**, and **Tab does not take the highlighted suggestion**. With hover driving `activeIndex`, the popup opens right where the pointer already is, so Enter took a contact the reader never navigated to and `aria-activedescendant` announced it; and stealing Tab meant the only way out of the To field was dismissing a popup the reader may not know is open. Hover is `hover:bg-background` styling only.
- **`onfocus` does not open the popup.** Tabbing into a field selects its whole value, putting `selectionStart` at 0, so the popup would open against the _first_ address in the list. Typing or clicking opens it.
- The popup uses a border and the `surface`/`background` contrast, **never a drop shadow** (`tasks/prd-ui-ux.md`'s Shape & Depth rule; `grep shadow src/` should stay empty).
- An option's `onmousedown` calls `preventDefault()`. Without it, the input's `blur` closes the popup before the click that is choosing an option ever lands.
- Both the combobox input and the `+ Cc` button carry `aria-expanded`, so **`button[aria-expanded=false]` is not a unique selector** — the `+ Cc` toggle has `id="cc-toggle"` and the compose form has `id="compose-form"` (the shell's logout form is the first `form` in the document) precisely so a browser check can address them. Keep those ids.
- When the To popup is open it is absolutely positioned **over** the `+ Cc` button, so a click there hits the suggestion. Move focus off the field first (that's what the demo does) — this is real behaviour, not a test artifact.

## The page and the action

- Cc collapsed means **not rendered**, so the form submits no `cc` field; the action reads a missing field as `''`, the same as an empty one. Nothing hidden holds a stale value. It opens itself when a returned draft has a Cc, so a rejected submit can't hide typed addresses behind a closed toggle.
- **The Send button is `disabled` only in the browser** (`browser && !validation.valid`). An unconditional `disabled` is server-rendered against the empty draft, so a client with no JavaScript gets a button it can never re-enable and the action — the real enforcement — becomes unreachable. Don't drop the `browser` guard.
- Validation _messages_ are gated on a per-field `touched` flag (one delegated `oninput` handler on the form, keyed off the input's `name`); the _button_ is gated on validity alone. Marking every field touched on any keystroke made typing the first character of an address pop up a complaint about the missing subject — don't go back to that.
- **The `send` action validates the session itself.** It mutates nothing in US-H01, but SvelteKit runs an action _before_ any `load`, so `(app)/+layout.server.ts` cannot protect it, and US-H02 turns this body into a real send. The check is built in now so that story can't forget it. Same trap as US-G03's `+server.ts` and US-G04's delete — see `docs/notes/auth.md` and the cross-cutting rule in `CLAUDE.md`.
- **Every return path echoes the draft back** (`ComposeResult` in `+page.server.ts` keeps success and failure structurally identical, so the page can read `form?.errors` off the `ActionData` union without narrowing). That is US-H02's FR-4 arriving early: the page seeds its field state from `form?.draft`, so a failed send re-renders what was typed. Keep new outcomes in that one shape.
- The page seeds `$state` from `form?.draft` inside `untrack(...)`: a deliberate one-time seed, not a binding — once the owner is typing, the field is the source of truth. The form is a plain (non-`enhance`d) POST, so every result arrives with a fresh mount.
- `+ Cc`'s and Send's styling: Send uses the accent, per the compose PRD's design note; a discard/remove affordance (US-H05) should use `text-danger`. Validation messages and other prose are **sans** (`font-sans text-sm`, matching `ErrorMessage.svelte`); only addresses, labels and the like are monospace — a subject is prose, so the Subject input is sans too. Any control that sets `focus-visible:outline-none` must add a visible substitute (`focus-visible:border-*`), as every other control in this app does.

## Entry point and demo data

- The **Compose link lives in the `(app)` shell's top bar**, unlike the search box and the thread list, which were deliberately pushed down into the inbox subtree. Writing a new message is not part of the inbox list's state, so every `(app)` route should offer it from the same place.
- `seed-f03-demo.mts` now also seeds three contacts on the throwaway `@f03-demo.example` domain (two with names sharing a fragment, one with no name) and removes them in `--cleanup` by that address pattern — never by anything that could match a real correspondent. Reuse them for compose demos instead of seeding contacts by hand.

## The send (US-H02)

- **The action's three steps are ordered on purpose: validate → send → store.** Storing after delivery means a failure of the write leaves a delivered-but-unrecorded message; storing first would mean either rolling back a committed row or leaving an `emails` row for mail that never went out. A phantom sent message is the worse lie, so the write goes last — and the "delivered but not stored" case therefore returns `sent: true` with a **`warning`**, never an `error`. Nothing on that path may read as "not sent": the owner's next move would be to send the same mail again.
- Only the **send** failing means nothing happened, so only that path returns `fail(502)` with the draft for a retry (FR-4). It is a `fail`, not a thrown error — an unhandled throw renders the error page and the composed message is gone.
- `getOutboundSender()` in `server/email/resend.ts` is a **server-side constant** (`casey@caseynazelrod.com`), like `AUTH_SENDER_EMAIL` and for the same reason: `from` is the one field of a send that must never be influenced by request input. It is on the apex because Resend holds the apex MX, so a reply comes back through the inbound webhook into this inbox.
- **Resend rewrites `Message-ID`; it preserves `In-Reply-To` and `References`.** Measured, not assumed (US-H02): a send carrying `Message-ID: <probe-custom@caseynazelrod.com>` arrived stamped `<…@email.amazonses.com>` (Resend sends via SES), while the same probe's `In-Reply-To` arrived verbatim. Reading the real id back is not an option either — `emails.get()` 404s for several seconds after a send and an action cannot wait. Consequences, all load-bearing for US-H03:
  - `emails.message_id` stores the id **this app mints** (`server/outbound/message-id.ts`, `<uuid@sender-domain>`, brackets included because that is the form `In-Reply-To` arrives in). Storing Resend's returned email id instead would store a value from a namespace that never appears in a header, which no reply could ever cite.
  - The send seeds the outgoing **`References`** chain with that minted id even on a brand-new message with no parent. A replying client copies the parent's `References` into its reply, so that is the one header-level route back to a message this app sent — `inbound/store.ts` matches `In-Reply-To` _and_ `References` against `emails.message_id`. Don't "clean up" that unusual-looking `References` on a first message.
  - A reply's `In-Reply-To` will cite SES's id, which this app never learns, so **the header path is best-effort and the 30-day same-subject fallback is what usually catches a reply.** That is why `storeSentEmail` writes the _normalized_ subject to `threads.subject` like every other thread write.
- **A new message always starts a new thread**; there is no same-subject fallback on the way out. Inbound has to guess because the sender chose the headers; the owner's intent is known exactly — a reply passes the parent's `threadId` (US-H03), composing from scratch passes null.
- **`text: ''` is a 422.** Resend answers `Missing \`html\` or \`text\` field`for an empty body, and the draft rule accepts a subject-only message ("a subject **or** a body") — so`sendOutboundEmail`substitutes a single space on the wire. Only on the wire:`emails.body_text`keeps the original empty string, so the thread view still renders its "no body" line instead of a phantom space. The same shape as the`(no subject)` placeholder the action applies for the mirror case.
- **Text only, no HTML part.** The body is a `<textarea>`, so the message _is_ plain text; an HTML twin would add an escaping step and a second body that can disagree with the first. `emails.body_html` is null for these rows and the thread view falls back to `body_text` (`bodyPlainText`). The compose PRD's open question — always generate a text part alongside HTML — is satisfied trivially in this direction; if rich composition ever lands, the _text_ part is what has to keep being generated.
- `touchThreadForSentMessage` **recomputes** `threads.is_read` where the inbound `touchThreadForNewMessage` forces it false: a sent message is read, so it must not re-flag a caught-up thread, and it must not mark a thread with unread siblings read either. It is also what makes a new outbound-only thread read, since `createThread` always writes `is_read = false`.
- A **successful** send clears the fields (the page seeds `$state` from `form?.draft` only when `form?.sent` is falsy). Leaving a sent draft in place hands the owner a loaded form whose only obvious gesture is Send again. Failure keeps it — that is the point of FR-4.
- `upsertAutoContact` (renamed from `upsertContactFromInbound`) now has two callers: the inbound webhook and this send path, which upserts every To and Cc address inside the same transaction (FR-5).
- `src/lib/server/outbound/verify-outbound-send.mts` is this area's check (29 checks; live DB, self-cleaning). It does **not** send mail — real delivery is proved in `docs/demos/US-H02.md`, which drives a browser send and then confirms Resend's own `last_event` is `delivered`. Don't assert the delivered copy looping back through the inbound webhook: it does arrive (the apex MX is Resend), but the round trip measured anywhere from 5 to over 60 seconds, and a demo that fails on a slow mail hop cries wolf.

## Reply (US-H03)

- **The Reply link carries one thing: `?replyTo=<email id>`.** Everything else a reply needs — recipient, subject, quoted text, the thread to join, the `In-Reply-To` to cite — is re-read from that row by `loadReplyTarget`, in the `load` _and_ again in the `send` action. Nothing round-trips through a hidden field. `threadId` is the reason the rule is absolute rather than stylistic: it decides where a sent message lands, and accepting it from a form is accepting "file this reply in whatever thread the client says".
- **The parameter rides in the form's `action` URL (`?/send&replyTo=…`), not in a hidden input.** A form action's query _replaces_ the page's, so a bare `?/send` lands the rejected submit on `/compose?/send` with no `replyTo`: the fields come back (FR-4 holds) but the page has silently stopped being a reply, and the next Send opens a new thread with the same subject and no `In-Reply-To`. Carrying it in the action URL also means the load and the action read the id from the same place. `docs/demos/US-H03.md` proves the failure path still says "Reply".
- **Threading is done by the row, not the header.** `storeSentEmail` gets `parent.threadId`, which is the half that cannot fail; `In-Reply-To` is set from `parent.messageId` and is the best-effort half (SES rewrites `Message-ID` on the way out — see the US-H02 section above — so it only survives when the parent is _inbound_ and its id is one a real client minted). Measured while building H03: replying to an inbound message and letting the delivered copy loop back through the production webhook threads it onto the same conversation on that header alone.
- A reply whose parent has since been **deleted** degrades to a new thread rather than failing the send, and an unknown `?replyTo=` opens the ordinary compose screen rather than a 404 — the message the owner wrote is still worth delivering. `getVisibleEmailById` excludes soft-deleted rows, so a deleted message is not a reply target at all: quoting one would resurrect text the owner has already removed from the thread.
- `src/lib/compose/reply.ts` is pure like `addresses.ts` and holds only the text shaping: `replySubject` (its `SUBJECT_PREFIX` is deliberately **narrower** than `inbound/threading.ts`'s — that one collapses every localized variant onto a grouping key, this one writes a subject a human reads, and re-prefixing `Aw: Angebot` would be worse than the criterion requires), `quoteOriginal`/`replyBody` (`> ` per line, blank lines as a bare `>`, two blank lines above so the owner top-posts), and `replyRecipients` (an outbound parent replies to its own **To**, minus the owner's own address — a "reply" addressed to `from` is a mail to oneself). Checks live in `verify-compose-addresses.mts`, per the one-script-per-area rule.
- **Cc is not carried over.** Reply, not Reply-all: silently re-addressing everyone the original copied is the mistake in a mail client that cannot be taken back, and `+ Cc` is one click away.
- The quoted body is `bodyPlainText(parent.bodyText, parent.bodyHtml)` — the same rendering the thread view shows — because a plain-text send has nowhere to put markup.

## Forward (US-H04)

- **Reply and forward are one mechanism with two parameters.** `?replyTo=<id>` and `?forwardOf=<id>` are read by the same `composeSource(url)` in the `load` _and_ in the `send` action, resolve through the same `loadParent`, and produce a single `data.context` (`{ mode, emailId, threadId, draft, attachments }`) that the page renders from. There is no `data.reply` any more. Everything the reply section above says about the id being the _only_ thing the browser chooses — and about it riding in the form's **action URL** (`?/send&forwardOf=…`) rather than a hidden input — applies unchanged, and matters _more_ for a forward: the attachments are looked up from that id at send time, so losing it across a rejected submit would silently drop the files. If both parameters are present `replyTo` wins; one deterministic answer beats an error page for a URL only a hand-edit can produce.
- **To is empty and nothing else is.** A forward's premise is a new recipient. Pre-filling the original sender (or its recipients) is one un-noticed Send away from mailing a private message back where it came from, so `forwardDraft` sets `to: ''` and the Send gate does the rest — a pre-filled forward is deliberately _not_ sendable until the owner types someone.
- **A forward starts a new thread and cites nothing.** `threadId: null` and `inReplyTo: null`, both keyed off the same `forwarding` flag. Joining the original thread would file a message to a third party under a conversation they were never part of; an `In-Reply-To` pointing at a message the recipient has never seen would ask their client to thread it under something they don't have. This is the one place a reply and a forward diverge in `storeSentEmail`'s input.
- `forwardSubject` shares `replySubject`'s `SUBJECT_PREFIX` and its outermost-prefix-only rule, so `Fwd:`/`Fw:` is never doubled while `Re: lunch` still becomes `Fwd: Re: lunch`. `forwardBody` writes the `---------- Forwarded message ----------` block — From/Date/Subject/To, a field with nothing to say omitted rather than printed empty — and passes it through the **same** `quoteBlock` as the body under it, so the whole forwarded unit reads as one quoted thing. Both are in `lib/compose/reply.ts`, still pure, still checked in `verify-compose-addresses.mts`.
- **Attachments are copied, not aliased.** `loadForwardedAttachments` reads the parent's files out of R2 _before_ the send; `storeForwardedAttachments` writes them back under a **new** `outbound/<new email id>/<source attachment id>-<slug>` key after it. Two rows pointing at one object would mean deleting either message's blob silently empties the other — an aliasing bug that only surfaces long after the forward. Both halves inject their R2 calls (`server/r2` reads env at import time), matching `inbound/attachments.ts`.
- **The two halves have opposite failure policies, and that is the point.** A read failure before the send is **fatal** — `fail()` with the draft still on screen — because mail cannot be un-sent and a forward whose file quietly vanished is a message that says "see attached" and doesn't. A write failure after the send is **best-effort**: the mail is already out, so it returns `sent: true` with a `warning` (which is why the page now renders a warning _alongside_ the thread link rather than instead of it). `MAX_FORWARDED_ATTACHMENT_BYTES` (25 MB) is checked against the stored `size_bytes` before any download, so an oversized forward costs one query rather than 25 MB of transfer.
- Resend gets the files as `content` (bytes), never as a `path` pointing at a presigned R2 URL: a URL makes delivery depend on a link's own expiry clock and on Resend reaching the bucket, and a fetch failure would surface as a missing file rather than a failed send.
- The compose screen lists the carried files **read-only**. There is no remove control because the list is looked up server-side from `?forwardOf=` — a control offering to drop one could only lie about what will be sent. US-H05 adds the picker, and the remove affordance belongs with it.

## Attachments the owner picks (US-H05)

- **The bytes never go through the app.** The browser asks `POST /compose/uploads` for a presigned PUT, uploads straight into R2, and the form submits only the object **key**. That is not an optimization: the app runs on Vercel, whose functions cap a request body around 4.5 MB, so a 25 MB attachment posted through the form action could not arrive at all. (The same ceiling is why the _download_ endpoint 302s to a presigned GET instead of proxying bytes — see `docs/notes/thread-view.md`.)
- **A presigned PUT is a cross-origin request, so the bucket needs a CORS rule** allowing `PUT` with a `content-type` header from this app's origins. `src/lib/server/r2/set-cors.mts` is the single description of that policy — but the repo's `R2_ACCESS_KEY_ID` is an _Object_ Read & Write token and `PutBucketCors` needs _Admin_ Read & Write, so the script 403s and the policy is applied by hand in the Cloudflare dashboard. **Without it every upload fails with an opaque network error before it starts**; if attachments suddenly stop working on a new bucket, check this first. See `docs/notes/infrastructure.md`.
- **The cost of direct upload is that the key is request input, and `server/outbound/uploads.ts` is the module that refuses to take any of it on trust:**
  - the **key** must match `isPendingAttachmentKey` (`outbound/pending/<uuid>/<slug>`, minted only by the endpoint), so a hand-written POST cannot name an `inbound/…` object and mail out someone's file;
  - the **size** and **content type** come from R2's own HEAD, never the form, so a client understating a 40 MB file buys nothing — and the HEADs all run _before_ any download, so an oversized send costs metadata requests rather than 25 MB of transfer;
  - the **filename** is the one thing only the client can know, and it is sanitized (`composeAttachmentFilename`, the same reduction inbound applies to a sender-supplied name);
  - `PendingAttachment.sizeBytes` **does** round-trip through the form, and it is display bookkeeping only — it exists so a refused send can re-render the list with real sizes instead of "0 B". Nothing the send does depends on it.
- **`MAX_ATTACHMENT_TOTAL_BYTES` (25 MB) is per _message_, not per source**, and it lives in the pure `lib/compose/attachments.ts` because the browser gates on it too (`server/outbound/attachments.ts` re-exports it). A forward's carried files count against it: the picker gets them as `otherBytes`, and the action loads the picked files first so `loadForwardedAttachments` can be given their real total as `existingBytes`. `MAX_FORWARDED_ATTACHMENT_BYTES` and `ForwardedAttachmentsTooLargeError` are gone — one limit, one error.
- **Both sources are the same thing from `OutboundAttachment` down.** `storeOutboundAttachments` (renamed from `storeForwardedAttachments`) writes the message's own copy under `outboundObjectKey` for either. A picked file is therefore **copied out of `outbound/pending/`, not left there**: a settled attachment must not live under a prefix whose whole meaning is "not yet claimed by a send" and which is safe to sweep.
- **The pending object is dropped after the send — except when the copy failed.** Then it is the only remaining copy of a file the recipient already has, so it is left in place; leaking an object under the pending prefix is cheap, deleting the owner's last copy of their own attachment is not.
- **Failure policy matches the forward exactly**: reading a picked file is fatal _before_ the send (`fail()` with the draft and the file list still on screen — mail cannot be un-sent, and a message that says "see attached" and doesn't is the thing worth refusing over), everything after the send is best-effort with a `warning` and never reads as "not sent".
- **Send is unavailable while any picked file is unsettled — uploading _or_ failed** (`unsettledAttachments`, in the pure module so the page and the component cannot disagree). The hidden `attachments` field only carries files that already have a key, so sending past either state would produce a message that _lists_ a file it does not carry — the client-side twin of the "says see attached and doesn't" failure the server refuses a send over. A failed row is cleared by removing it; that is why Remove is on every row, failed ones included. Still inside `+page.svelte`'s `browser &&` guard — with no JavaScript there are no uploads to wait for (and no picker; the field is inert without it, which is the honest degradation for a control whose whole job is an XHR).
- `AttachmentField.svelte` keeps the list in state and renders the hidden field from it, so **what submits is exactly what is on screen** — the same one-visible-source-of-truth rule `RecipientField.svelte` follows. The drop zone is paired with a real `+ Attach` button (`id="attach-button"`, input `id="attach-input"`) because drag-and-drop is unavailable to a keyboard and to most touch input. A failed upload stays in the list marked `upload failed` rather than vanishing, and blocks Send until it is removed. **Removing a row mid-upload** cannot send the DELETE (there is no key yet), so `settle()` sweeps the object when the PUT finally lands and finds its row gone — otherwise that object would sit in `outbound/pending/` forever with no send coming to claim or clear it.
- The forward's carried files stay a **read-only** list above the picker, for the reason US-H04 gave: they are looked up server-side from `?forwardOf=`, so a Remove there could only lie about what will be sent. The removable list is the picked one.
- Checks: the pure half in `verify-compose-addresses.mts` (key shape, filename sanitization, `parsePendingAttachments` on garbage/duplicates/negative sizes), the server half in `verify-outbound-send.mts` (R2 stubbed: key round-tripping, R2's size winning over the form's, the per-message limit spanning both sources, the post-send sweep and its swallowed failure).
- **The `$state` proxy trap this component fell into**, recorded because it cost a browser round to find and is invisible to typecheck and lint: `items.push(item)` puts a _proxy_ in the array, so the `item` reference the upload closure still holds is the raw object — `item.status = 'ready'` mutated the target without tripping the setter, and the row sat on "uploading…" forever with Send permanently disabled. `settle(id, patch)` looks the entry back out of `items` and writes through the proxy. See the cross-cutting rule in `CLAUDE.md`.
