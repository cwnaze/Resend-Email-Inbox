# Thread view — rendering, sandboxed HTML, remote images

## Thread view (US-G01)

- `src/lib/server/db/emails.ts`'s `listThreadEmails` is the thread's read query: non-deleted emails only, `received_at asc` with `id` as the tie-breaker (the sort key is a sender-supplied `Date:` header, so two messages can share a millisecond). Excluding soft-deleted rows _in the query_ is what makes "no visible messages" a `length === 0` answer the load can 404 on, using the same definition of "visible email" as `listInboxThreads`' inner join — don't reintroduce a separate filter in the load.
- `src/routes/(app)/inbox/[threadId]/+page.server.ts` 404s twice: unknown thread id, and a thread whose every message is soft-deleted. The second check runs **before** `markThreadRead`, so a navigation that can't render anything doesn't mutate read state on the way out. `src/routes/(app)/inbox/[threadId]/+error.svelte` is the boundary that renders both (route-scoped, so the copy can say "this thread" and offer the one useful action — back to the list).
- The header shows the **newest message's own `subject`**, never `threads.subject`: that column holds the normalized grouping key (lowercased, `Re:`-stripped). Any future thread-titled UI should do the same.
- Body rendering is decided **in the load**, not the component (same reason the list derives snippets server-side): US-G02 replaced the plain-text-only rendering with two mutually exclusive branches — see the HTML-rendering section below. `bodyPlainText`/`htmlToPlainText` are still what a text-only message renders through, and are explicitly not sanitizers; nothing in this view uses `{@html}`.
- New pure helpers in `src/lib/inbox/format.ts` (still no env/db/DOM, still shared by the load, the components and `verify-inbox-list.mts`): `bodyPlainText` (text body preferred, de-tagged HTML fallback — the same precedence as `bodySnippet`, so a row's preview and the message it opens can't derive from different halves of the row), `htmlToPlainText` (collapses horizontal whitespace, keeps line structure, caps blank runs at one), `addressListLabel` (null/empty/blank-only all collapse to `''` so the component renders no `cc` line rather than a dangling label), and `absoluteTime`. `decodeBasicEntities` decodes `&amp;` **last** — decoding it first double-decodes `&amp;lt;`.
- **The list/detail split is still not built, and it isn't just layout work.** A `+layout.server.ts` load runs _in parallel_ with the page load it wraps, so an inbox list living in `inbox/+layout.svelte` would render from a snapshot taken before the thread page's `markThreadRead` committed: the row just opened keeps its unread dot until some later navigation. Building the split means moving the mark-read mutation to a form action or adding an explicit invalidation first — which is US-G04's territory.
- `svelte/no-unused-props` also rejects a declared prop field a component never reads, not just an unused prop: `ThreadMessage`'s `Props` deliberately omits the `id` its parent uses as the `#each` key.
- `src/lib/server/db/seed-f03-demo.mts` (despite the F03 name) is the shared browser-demo seeder: read thread, unread thread, a three-message conversation (HTML-only second message carrying one remote and one `data:` image for US-G02's toggle, `cc`, soft-deleted third) and a `123456` login code. Since US-G03 it also uploads three tiny objects to the real R2 bucket and attaches two to the conversation's first message and one to its soft-deleted third (which must stay unreachable) — it builds its own `S3Client` from `process.env` because `$lib/server/r2` reads `$env/dynamic/private` and can't be imported under bare `tsx`, the same workaround `r2/verify.mts` uses. `--cleanup` removes the objects too, best-effort. `--hide-conversation` soft-deletes the conversation's messages to demo the empty-thread 404; `--cleanup` removes everything. It prints **no row ids** on purpose — a demo that pasted a generated UUID into a URL couldn't be re-run by `showboat verify`, so reach the thread by searching the list and clicking the row.

### HTML rendering and remote images (US-G02)

- The thread view renders a message's HTML in `EmailHtmlBody.svelte` (a sandboxed `<iframe srcdoc>`) and/or its plain text in a `<pre>` — **both is a valid state**, see the rule below. HTML is the richer rendering, which is the opposite precedence from `bodySnippet`/`bodyPlainText`: a _preview_ wants the cheapest readable form, not the richest. Don't "unify" the two precedences.
- **Body rendering is two independent decisions, never one either/or** — the either/or was the source of a whole family of bugs across six review rounds:
  - A **frame** is mounted when there is anything a frame could show: `hasVisibleText` or `hasLoadableImage`. Deliberately **not** "any blocked image": a body whose only image is a declared 1×1 tracker mounted a blank frame captioned "1 remote image blocked", whose only button existed to fire the beacon. Nothing to frame — an empty body, or one whose only image is an unresolvable `cid:` — leaves `html` null so the honest "no body" line renders instead.
  - The **text part** is dropped _only_ when `hasVisibleText`. Never on the strength of the image heuristic.
- **That second rule is load-bearing and must not be "optimized".** Earlier versions decided it from a size heuristic over the images, and every threshold was one attribute away from being bypassed (`width="4"`, then `width="17"`) — each bypass silently discarding a readable message with no way to reach it. A heuristic cannot win that argument, so it doesn't get to: a frame whose content can't be vouched for is shown **with** the text beneath it (`ThreadMessage` renders both), and the reader loses nothing either way. A "view in browser" stub showing under an image-only frame is the price, and it is the right trade.
- `hasLoadableImage` is deliberately weaker than "is definitely real": an image disqualifies itself by **declaring** a size at or below `TRACKING_PIXEL_MAX_PX` (16) on either axis, and is otherwise assumed it might show something. An _undeclared_ size stays ambiguous on purpose — a hero sized by the stripped `style` attribute is indistinguishable from a CSS-sized tracker — so the frame appears and the reader decides. Also excluded: no `src` at all (a removed `javascript:` one), inside a non-rendering subtree, and `cid:` references. Units and decimals (`600px`, `600.5`) are read as sizes because senders write them.
- **"Hidden" is not just `[hidden]`.** `isNonRendering` also covers `<dialog>` without `open` and `<datalist>` — both survive sanitization and render nothing, and counting their text as visible let `<dialog>Full invoice text</dialog>` suppress a readable text part in favour of a frame that drew nothing. Add to that helper rather than assuming `[hidden]` is the whole story. A hidden image's `src` is still **parked** (a `display:none` image is fetched by plenty of browsers) but is **not counted**, because the count is a claim to the reader and loading it would reveal nothing. `cid:`/`data:` images are never counted as blocked either.
- Text is measured by a **walk that skips `[hidden]` subtrees and short-circuits** on the first visible character (it runs per message per thread load, and a 220KB body is not unusual in email; an earlier clone-and-strip version copied the whole tree). It matters because `<div hidden>x</div>` survives sanitization and its "x" used to beat a readable text part, leaving a blank 24px frame. `style="display:none"` cannot be caught this way — `style` is stripped on write — and that limitation is documented on the helper rather than implied away.
- **`format.ts`'s `HTML_TAG` is deliberately the naive `/<[^>]*>/g`, and must stay that way.** A version that skipped quoted attribute values — so a sender-controlled `>` inside an attribute couldn't end a tag early and leak `2">` into a snippet — **backtracks catastrophically**: 6ms → **15 seconds** on 4000 bare `<` characters, in a helper that runs for every row of the inbox list, so one such body blocks the event loop and takes the whole inbox down. The leak is cosmetic now that the body choice is made in the DOM. (The naive form is itself quadratic on a long run of raw `<` — ~11s for 200KB — but that is unreachable through the write path, since DOMPurify escapes stray `<`, and it is what the app has shipped since US-F01. If it ever needs a bound, cap the _input length_, don't make the pattern cleverer.)
- `src/lib/inbox/srcdoc.ts` is pure (no env/db/DOM/**dependencies**) and owns `BLOCKED_IMAGE_ATTR`, `restoreBlockedImages` and `buildEmailSrcdoc`; `src/lib/server/inbox/html.ts` owns `prepareEmailHtml`, the server-only half (it pulls in DOMPurify). The split is what lets the component build the document without shipping DOMPurify to the browser, and lets `verify-inbox-list.mts` exercise both under bare `tsx` — so `server/inbox/html.ts` imports by **relative** path, same constraint as `server/db/inbox.ts`.
- **Image blocking is a read-path pass, not a write-path one.** `emails.body_html` keeps the sender's image URLs: "Load images" has to be able to put them back, and FR-3 wants the opt-in _per message_, which a stored-once-stripped body could not offer. So `prepareEmailHtml` runs on every thread load and returns `{ html, blockedImageCount }`.
- The parked URL lives on a `data-*` attribute **because** `SANITIZE_OPTIONS` sets `ALLOW_DATA_ATTR: false`: a sender who writes `data-dt-blocked-src` themselves has it stripped before this pass adds ours, so the only values that can ever be restored to `src` are the ones this app moved. Keep those two facts together — allowing data attributes would turn the restore step into a sender-controlled image loader. For the same ordering reason a `javascript:` src is already gone (DOMPurify's URI allow-list runs first), so parking can never reintroduce a scheme the sanitizer refused.
- `SANITIZE_OPTIONS` is exported from `src/lib/server/inbound/sanitize.ts` and shared by both paths, so a row written before that module existed can't be rendered under weaker rules than one written after. `prepareEmailHtml` re-sanitizing is deliberate, not redundant.
- `prepareEmailHtml` uses `RETURN_DOM_FRAGMENT` and walks the fragment — **not** a DOMPurify `afterSanitizeAttributes` hook. Hooks live on the process-wide DOMPurify singleton, and `removeHook(entryPoint)` pops whichever hook is _last_ rather than a named one, so once any second hook exists anywhere in the process the cleanup can remove the wrong one and leave this closure installed on the **write** path — quietly writing `data-dt-blocked-src` into stored bodies. The hook version was also only correct while nothing `await`ed between add and remove. Don't reintroduce it. (Fragment mode was checked byte-identical to string mode across the adversarial fixtures.)
- `data:` and `cid:` sources are never counted as blocked (bytes already present / a reference that reaches nobody) — counting them would show a "Load images" button that can't do anything. Remote `src`/`poster` on `video`/`audio`/`source`/`track` is dropped outright with no restore affordance: the story asks for an image opt-in, not a media one.
- The toggle is enforced **twice**: the attribute swap _and_ the srcdoc's CSP `<meta>` (`default-src 'none'`, `img-src data:` until the reader opts in). Keep both — the CSP is what still holds if some future markup path sneaks a `src` past the blocking pass.
- `sandbox="allow-same-origin"` with **no** `allow-scripts` is the containment. `allow-same-origin` is there so the parent can read `contentDocument` — to size the frame and to intercept link clicks; since scripting is off inside, nothing in there can use the shared origin.
- **A sandbox without `allow-popups` does not make links inert.** A plain `<a href>` navigates the frame _itself_, which sandbox always permits — verified in a browser: the remote page rendered inside the app's chrome and the frame went cross-origin, which also silently killed the height measurement. What prevents it is the srcdoc's **`<base target="_blank">`**: opening a new context is exactly what the sandbox blocks, so the worst case is "nothing happens", declaratively, before hydration and even if hydration never runs. `EmailHtmlBody`'s `interceptLinkClick` is the _upgrade_ (a real new tab via `window.open(..., 'noopener')`), never the guarantee — don't delete the `<base>` on the grounds that the handler covers it. It cancels every link click but only opens **absolute http(s)** URLs: a relative path or a bare `#anchor` (a newsletter "back to top" link) survives sanitization and would otherwise resolve against this app's own origin and open a pointless tab showing our own inbox.
- That handler's element check is **duck-typed, not `instanceof Element`**: the frame is its own realm, so `instanceof` against this document's `Element` is always false for nodes from inside the frame and the guard swallows every click — which looks like working code and silently restores the takeover. (This bit once already.)
- **Height comes from the body box, never `documentElement.scrollHeight`.** The root's scroll height is floored at the frame's own viewport height, i.e. it reports back whatever height was last set: the frame could then only grow, never shrink, and short messages were padded to the initial guess. The srcdoc body also sets `display: flow-root` so the last child's bottom margin is _inside_ the measured box — without it `body.scrollHeight` stops above the final line and the frame clips it. Measure on `load`, re-measure with a `ResizeObserver` on the body (an image finishing after `load` is the common case), and also measure from an `$effect` when `readyState` is already `complete`: on a server-rendered page the srcdoc can finish loading before hydration attaches `onload`, and `load` fires once.
- `template` is forbidden **only in `prepareEmailHtml`'s own options, never in the shared `SANITIZE_OPTIONS`.** The read path needs it gone because a `<template>` keeps its children in a separate `content` fragment that `querySelectorAll` cannot reach, so a remote `<img>` in there was neither parked nor counted. But forbidding it on the write path is **data loss**: DOMPurify's default `FORBID_CONTENTS` includes `template`, so the text inside it is deleted from `body_html` — the only copy this app has — and AMP-for-Email bodies (`<template type="amp-mustache">`) carry their content exactly that way. Since the read path re-sanitizes anyway, forbidding it there costs nothing and forbidding it on write cannot be undone.
- `measure()` returns early while `readyState === 'loading'` **and for `about:blank`** (the document an iframe holds before its `srcdoc` navigation, which is already `complete` — the mount-time effect would otherwise measure an empty body and write the 24px floor), and the `$effect` reads `srcdoc` so it tears down the observer/listener bound to the outgoing document. Without both, a `ResizeObserver` callback landing mid-toggle measures the new, still-empty document and collapses the message to the 24px floor.
- The click interceptor also listens for `auxclick` (middle-click, `button === 1`): otherwise the reader's "open in a background tab" reflex hits the sandbox's silent block and reads as a dead link.
- The images-loaded CSP adds `upgrade-insecure-requests`. The app is https, so an older newsletter's `http://` image would be killed as mixed content _after_ the reader opted in and after the "blocked" notice has gone — a broken image with no way to retry.
- The iframe document is forced light-on-white regardless of the app theme: email HTML brings its own colours and assumes a light canvas, so a dark one yields dark-on-dark text. The blocked-image placeholder is styled via an `img[data-dt-blocked-src]` **attribute selector**, so restoring `src` removes the placeholder styling by construction — no second marker to remember to strip.

### Attachments and download (US-G03)

- Each message that has attachments renders `AttachmentList.svelte` **below** its body: filename + `formatFileSize(size_bytes)` per row, in the metadata (monospace) face, and nothing when the list is empty. A message whose attachments all failed to upload at ingest has no rows and correctly shows nothing — inbound attachment storage is best-effort (see `docs/notes/inbound.md`).
- The load fetches them with **one** `listAttachmentsForEmails(db, everyMessageId)` and groups by `emailId`, rather than `getAttachmentsByEmailId` per message: Turso is remote, so per-message lookups are per-message round trips (same reason `listInboxThreads` is one query).
- **`r2_object_key` never crosses the wire.** The client gets `{ id, filename, size }`; the key is resolved server-side by the download endpoint. The size is formatted in the load, so the component holds a string and no formatting logic.
- `formatFileSize` (in the pure `lib/inbox/format.ts`) uses **decimal** units (1 KB = 1000 B) to agree with what the sender's OS and mail client reported, one decimal place from KB up, and clamps at `TB` rather than indexing off the unit array. It guards non-finite and negative input even though `size_bytes` is written from the bytes actually downloaded — a `NaN` in a message header would render `NaN undefined`.

#### The download endpoint

- `GET /inbox/[threadId]/attachments/[attachmentId]` (`+server.ts`) presigns and **302s to R2**. The bytes never pass through the function: a serverless invocation has a 4.5MB response ceiling and a 10s budget, and a 20MB attachment would blow both.
- **Presigning happens per click, deliberately not in the thread load.** A signed URL expires and a thread page sits open in a tab for hours, so a URL minted at load time would be dead by the time it was clicked, with nothing to explain why. Per-click also means a thread of twenty attachments costs zero signatures to render. Expiry is **60s**, not the module's 15-minute default, because the redirect is followed immediately and the URL lands in browser history and R2 access logs.
- **`(app)/+layout.server.ts` does NOT protect this route, and that is not a SvelteKit quirk to work around but a rule to remember: a layout `load` runs for pages, never for a `+server.ts` request.** So this endpoint calls `validateSession` itself. This is the one legitimate exception to the auth notes' "never add a second parallel check" — without it this route is an unauthenticated hole in the route group handing out the owner's mail to anyone who guesses two UUIDs. **Any future `+server.ts` added under `(app)/` needs the same line.** It answers **401**, not a redirect to `/login`: the request is a link click expecting a file, and a login page delivered as a download is a worse answer than a refusal.
- The lookup is `getThreadAttachment(db, threadId, attachmentId)` — thread id **in the query**, joined to `emails` with `is_deleted = false`. Holding an attachment id is not authorization to fetch it through any thread's URL, and a soft-deleted message's files stop being reachable at the same moment the message does (same definition of "visible email" as `listThreadEmails`). A wrong thread id, a soft-deleted parent and an unknown id are all one `undefined` → one 404, so a probe can't tell them apart.
- `getR2SignedDownloadUrl` now takes an options object (`{ expiresInSeconds, contentDisposition, contentType }`) as well as the old bare-number second argument. Both overrides are S3 `response-*` **signed query parameters**, so they are covered by the signature and whoever holds the URL cannot change them — that is what lets this app fix the saved filename without the stored object carrying it.
- `server/inbox/download.ts` builds those two header values, and is pure with no dependencies (like `srcdoc.ts`) so `verify-inbox-list.mts` can exercise it under bare `tsx` — hence **relative** imports only, same constraint as `html.ts`.
  - **Both `filename` and `content_type` are sender-controlled columns being interpolated into a header**, which is where a stray `"`, backslash, CR or LF stops being cosmetic and becomes response splitting. `attachmentContentDisposition` escapes at the point of use rather than trusting `inbound/attachments.ts`'s write-time `attachmentFilename` — rows written before that sanitizer existed would otherwise be trusted — and `downloadContentType` collapses anything that isn't a bare `type/subtype` to `application/octet-stream`.
  - It emits **both** RFC 6266 parameter forms: the quoted ASCII `filename` (non-ASCII replaced with `_`) for clients without RFC 5987, and the percent-encoded `filename*` every current browser prefers, so `rapport-café.pdf` survives instead of arriving as underscores.
  - Always `attachment`, **never `inline`**, for every content type. The bytes and their `Content-Type` both come from the sender, so `inline` would let a sender have a document rendered by the browser. (It is served from R2's origin, so an `inline` HTML attachment could not script this app either way — but the story asks for a download and this is the smaller surface.)
- **`AttachmentList` carries `data-sveltekit-reload`, and it is load-bearing.** The href is an internal route with no page component, so without it the client-side router would treat a click as an SPA navigation to a non-page. The attribute forces a real browser navigation, which is what lets the browser follow the 302 and honour R2's `Content-Disposition`.
- The href is built in the **component** with `resolve('/(app)/inbox/[threadId]/attachments/[attachmentId]', …)`, not in the load: `svelte/no-navigation-without-resolve` rejects `href={someString}` even when the load already resolved it, so the URL cannot be assembled server-side. That is why `threadId` is back in the load's payload and threaded through `ThreadMessage` — the one reason it is there.
