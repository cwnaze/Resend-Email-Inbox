## Codebase Patterns
- This SvelteKit toolchain (current `sv create` output, kit ^2.63) configures the Vite plugin and adapter directly in `vite.config.ts` — there is no `svelte.config.js`. Adapter/compiler options go there instead.
- `@sveltejs/adapter-vercel` runtime auto-detection rejects Node versions outside 20/22/24; pass an explicit `runtime` (e.g. `'nodejs22.x'`) to the adapter if the build/dev machine runs a newer Node.
- `.prettierignore` excludes `/tasks/`, `/agents/`, and `/docs/demos/` (PRDs, agent process files, and showboat demo logs) from the app's lint/format scope.
- When writing showboat `exec` blocks meant to be reproducible via `showboat verify`, strip timestamps/durations/PIDs from captured command output (grep/sed) before showboat records it.
- Real secrets (Turso URL/token, etc.) live only in the gitignored root `.env`; `.env.example` tracks variable names with empty values. Never let `showboat exec` capture raw `.env` contents or a connection string into a committed demo doc — pipe drizzle-kit/db output through `grep -v`/`sed` to redact if needed, and grep the demo file for secret-shaped strings before committing.
- Drizzle/Turso: `db` client lives at `src/lib/server/db/index.ts` (server-only import), schema at `src/lib/server/db/schema.ts`, config at root `drizzle.config.ts` (`dialect: 'turso'`). `npm run db:push` applies schema directly (no migration files generated); use `npm run db:generate` if versioned SQL migrations are ever needed.
- R2/Cloudflare object storage is private in this project — no `R2_PUBLIC_URL_BASE`/custom domain. Any story that needs to let the browser fetch/download an R2 object must call `getR2SignedDownloadUrl` (in `src/lib/server/r2/index.ts`) on demand; never assume a stored permanent public URL exists. `tasks/*.md` and `agents/prd.json` wording has been updated repo-wide to say "presigned URL" instead of "public URL" for attachments.
- SvelteKit's `$env/dynamic/private` only resolves inside a Vite/SvelteKit runtime — a standalone `tsx`/`node` script can't `import` app modules that pull in `$env/*`. For one-off infra smoke tests (e.g. `src/lib/server/r2/verify.mts`), read `process.env` directly and run via `node --env-file=.env node_modules/.bin/tsx <script>` instead.
- This repo has no linked Vercel project (no `vercel` CLI, `.vercel/project.json` absent) — any acceptance criterion requiring env vars "in Vercel project settings" can only be verified/set by the project owner; note it as an outstanding manual step rather than blocking `passes: true` on it.

- **Learnings for future iterations:**
  - GNU-style `tr -d '\r'` behaves fine on this machine's `tr`, but when capturing `curl -i` output in a `showboat exec` block for later `showboat verify` reproducibility, the raw `\r\n` line endings in HTTP headers must be stripped (e.g. `tr -d '\r'`) *in the exact command that gets recorded* — a block recorded without stripping will show a spurious mismatch on `showboat verify` (expected has no `\r`, actual re-run does) even though the visible text looks identical in a terminal. Always diff-check `od -c`/hexdump when a `showboat verify` mismatch shows textually-identical expected/actual.
  - `showboat pop` only removes the single most recent entry — if you exec several blocks in a row and then need to fix an earlier one, `pop` won't reach past the later ones already appended; it's simpler to hand-edit the demo `.md` file directly (delete the stale block) than to chain multiple `pop`s, and hand-editing a showboat-generated `.md` file is safe as long as you don't touch the `showboat-id` HTML comment.
  - Route-protection stories that land before their backing DB table's story is merged (e.g. this story before US-D01) should scope their check to what's actually available (cookie presence) and explicitly note in `prd.json`/progress which later story upgrades it to full validation — don't block on or fake a DB lookup that would break the moment the table doesn't exist yet on `main`.
