# Resend Email Inbox — Project Notes

## Stack

- SvelteKit (Svelte 5, runes mode forced via `vite.config.ts`'s `sveltekit({ compilerOptions: { runes: ... } })`), TypeScript, Tailwind CSS v4 (via `@tailwindcss/vite`, imported in `src/routes/layout.css` and pulled into `+layout.svelte`), `@sveltejs/adapter-vercel`.
- Package manager: npm. Scripts: `npm run dev`, `npm run build`, `npm run check` (typecheck via svelte-check), `npm run lint` (prettier --check + eslint), `npm run format`.

## Gotchas

- This SvelteKit toolchain (current `sv create` output) configures the Vite plugin and the adapter directly in `vite.config.ts` — there is **no `svelte.config.js`** in this project. If you need to change adapter options or compiler options, edit `vite.config.ts`.
- `@sveltejs/adapter-vercel`'s runtime auto-detection only supports Node 20/22/24. If the local dev machine runs a newer Node (e.g. v26), `npm run build` fails with `Unsupported Node.js version` unless the adapter is given an explicit runtime. This is already set: `adapter({ runtime: 'nodejs22.x' })` in `vite.config.ts`. Don't remove it.
- `.prettierignore` excludes `/tasks/`, `/agents/`, and `/docs/demos/` — those are PRD/agent-process files and showboat demo logs, not app source, and are intentionally left unformatted by the app's prettier config.
- `docs/demos/<STORY_ID>.md` files are showboat proof-of-work logs (one per user story). When capturing command output in a showboat `exec` block for later `showboat verify` reproducibility, strip anything non-deterministic (timestamps, build durations, PIDs) with `grep`/`sed` before showboat records the output — otherwise `showboat verify` will fail on a re-run even though nothing is actually broken.

## Database (Turso / Drizzle)

- `src/lib/server/db/index.ts` exports `db`, a `drizzle-orm/libsql` client built from `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` read via `$env/dynamic/private` (not `$env/static/private` — keeps the module importable even in contexts where those vars aren't statically inlined). Only import this from server-only code (`+page.server.ts`, `+server.ts`, `src/lib/server/**`).
- `src/lib/server/db/schema.ts` is the single Drizzle schema file; `drizzle.config.ts` (repo root, `dialect: 'turso'`) points at it and at `./drizzle` for generated migrations.
- Full schema (since US-D01): `contacts`, `threads`, `emails`, `attachments`, `auth_codes`, `sessions`, per `tasks/prd-data-model.md`. Booleans are `integer({ mode: 'boolean' })`, JSON address-list columns are `text({ mode: 'json' })`, timestamps are `integer({ mode: 'timestamp_ms' })`. Declare indexes via the `sqliteTable(name, columns, (table) => [index(...), uniqueIndex(...)])` array-builder form (current drizzle-orm API), and FKs via `.references(() => otherTable.column)` on the column definition. libSQL/SQLite does not enforce FKs per-connection by default — any code (including one-off verification scripts) that depends on FK rejection must `PRAGMA foreign_keys = ON` on that connection first. `src/lib/server/db/verify-schema.mts` is a standalone script (same `process.env`-reading, `tsx`-run pattern as `src/lib/server/r2/verify.mts`) that smoke-tests the live schema — extend it rather than writing new ad hoc scripts for future schema changes.
- Real Turso credentials live only in the gitignored root `.env` (never commit them); `.env.example` documents the variable names with empty values.
- `npm run db:push` applies the schema directly to the configured Turso database (no migration files); `npm run db:generate` emits SQL migration files under `./drizzle` if a versioned-migration workflow is needed later; `npm run db:studio` opens Drizzle Studio.
- Both `drizzle.config.ts` and `src/lib/server/db/index.ts` throw at startup if either `TURSO_DATABASE_URL` or `TURSO_AUTH_TOKEN` is missing — a remote Turso connection needs both, so failing fast on either avoids a confusing runtime error from `@libsql/client` later.
- If a future story switches to `npm run db:generate` (versioned migrations instead of `db:push`), commit the generated `./drizzle/*.sql` files and the `./drizzle/meta` journal — they're a source-of-truth migration history, not disposable build output, so `./drizzle` should NOT be gitignored once it's in use.

## Object storage (Cloudflare R2)

- `src/lib/server/r2/index.ts` exports three server-only utilities: `uploadToR2(key, body, contentType?)`, `deleteFromR2(key)`, and `getR2SignedDownloadUrl(key, expiresInSeconds?)` (default 15 min). Built on `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` against R2's S3-compatible API at `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`.

Any place the app needs to let the browser fetch/download an object must call `getR2SignedDownloadUrl` on demand rather than storing a permanent URL. - Required env vars: `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET_NAME` (read via `$env/dynamic/private`, same pattern as the Turso vars). The module throws at import time if any are missing.
- Only import `src/lib/server/r2` from server-only code (`+page.server.ts`, `+server.ts`, `src/lib/server/**`) — same rule as the `db` client.

## Inbound webhook (Resend / Svix)

- `src/lib/server/webhooks/svix.ts` (US-E01) is the **only** place a webhook signature is verified: `verifySvixRequest(request)` reads `svix-id`/`svix-timestamp`/`svix-signature`, reads the body as **text**, and returns `{ ok: true, payload, rawBody } | { ok: false, reason }`. Three things to preserve:
  - It consumes the request body itself, as raw text. The Svix signature covers the exact bytes Resend sent, so `request.json()` followed by a re-serialize will not verify. A `Request` body can only be read once — callers must use the returned `payload`/`rawBody` and never call `request.json()` before or after.
  - `payload` exists only on the `ok: true` branch by construction, so US-E02..E05's ingestion code physically cannot reach an unverified body. Keep the result type discriminated rather than returning a payload plus a boolean.
  - `reason` is for `console.warn` server-side only. The endpoint returns a bare `401` with no detail — a failure reason tells an unauthenticated caller how to forge a better signature.
- The `RESEND_INBOUND_WEBHOOK_SECRET` read is **lazy** (memoized `Webhook` on first verify), not import-time, for the same reason as `email/resend.ts`: `npm run build` imports every `+server.ts` during method detection, so an import-time secret check would make the build require a real credential.
- `POST /api/webhooks/resend-inbound` (`src/routes/api/webhooks/resend-inbound/+server.ts`) is the gate; US-E02 onward hangs parsing/persistence off the verified `result.payload` inside it, and must not add a second parallel verification path.
- `src/lib/server/webhooks/verify-inbound-webhook.mts` smoke-tests the endpoint over HTTP against a running dev server (`WEBHOOK_BASE_URL`, default `http://localhost:5173`), using `svix`'s own `sign()` for the positive case. The load-bearing case is **tampered body + genuine signature → 401**: that's what proves the raw bytes are what's verified. Extend this script rather than adding new ad hoc webhook scripts.
- **Deployed and live** as of US-E01: the app is served from `https://mail.caseynazelrod.com` (Vercel, builds from `main`), the webhook is registered in the Resend dashboard against `POST https://mail.caseynazelrod.com/api/webhooks/resend-inbound`, and the real `whsec_…` secret is in both the local `.env` and Vercel project settings. Re-run the five-case suite against production with `WEBHOOK_BASE_URL=https://mail.caseynazelrod.com node --env-file=.env node_modules/.bin/tsx src/lib/server/webhooks/verify-inbound-webhook.mts` (5/5 as of the US-E01 merge).
- DNS split worth knowing before touching domains: Resend owns `send.` (sending), `links.` (click tracking), and the **apex MX** (receiving); the app has the `mail.` subdomain to itself. So **inbound addresses are on the apex** — `something@caseynazelrod.com`, never `@mail.caseynazelrod.com`. Don't move the app onto a name that also holds MX records: Vercel wants a CNAME for a subdomain, and a CNAME must be the only record at its name, so it would block the MX outright (use an A record if that's ever unavoidable).
- Still unconfirmed after US-E01: every test to date is this repo's own signing code hitting its own endpoint. That a **real** Resend delivery arrives and verifies (apex MX receiving; Resend's signature format matching `svix` in practice) needs a real email and a `200` in the Vercel function logs. US-E02 should capture that first real payload before writing a parser — the `{ type, data: { from, subject } }` object in `verify-inbound-webhook.mts` is a placeholder, not observed truth.

## Auth / route protection

- Every mailbox route lives under the `src/routes/(app)/` route group. `src/routes/(app)/+layout.server.ts` is the single choke point: it calls `validateSession(db, cookies)` and redirects to `/login` on `null`. Add new protected pages under `(app)/` and they inherit this automatically — no per-route auth code needed, and never a second parallel check.
- `src/lib/server/auth/session.ts` (real as of US-B05) owns the session **cookie**, as distinct from `sessions-store.ts` which owns the `sessions` **table**: `SESSION_COOKIE_NAME`, `SESSION_TTL_MS` (30 days, FR-9), `setSessionCookie`/`clearSessionCookie`, `validateSession(db, cookies, now?)` (hash the cookie token → look up the row → reject missing/unknown/expired), and `destroySession(db, cookies)` (delete the row + clear the cookie). Four things to preserve here:
  - The cookie's name and its `path`/`httpOnly`/`secure`/`sameSite` flags are defined **once** in this module, and both `verify-code` (set) and `logout` (delete) go through the helpers. `cookies.delete` with a different `path` than the cookie was set with silently does not delete it, so re-specifying the options at a call site is a real bug waiting to happen — don't.
  - `validateSession` returns plain `null` for missing, unknown, _and_ expired cookies. Distinguishing them for the caller would leak whether a given token ever existed, and route protection treats all three the same anyway.
  - Sliding expiration (FR-9) only writes once the session is past the halfway point of its TTL, not on every request — a per-page-view DB write buys nothing, and refreshing at the halfway mark still means anyone active within any 15-day span never expires. When it does refresh, it re-sets the cookie so the browser's copy matches the row.
  - `(app)/+layout.server.ts` clears the cookie before redirecting, so a stale token isn't re-sent on every subsequent request.
- `POST /api/auth/logout` (`src/routes/api/auth/logout/+server.ts`, US-B05) deletes the `sessions` row and clears the cookie, then `303`s to `/login` (303 so the browser follows with a GET — the app shell's logout control is a plain JS-free `<form method="POST">`). Deleting the row is the whole point of FR-8: clearing only the cookie would leave a live row that a copied token could still use. It lives under `/api/auth/` alongside `request-code`/`verify-code` — the old `/logout` route from US-J02 is gone.
- `src/lib/server/auth/auth-codes.ts` and `src/lib/server/auth/sessions-store.ts` (US-B01) are the Drizzle query helpers for the `auth_codes`/`sessions` tables. Each takes the db handle as its first argument, typed as `Database` from `src/lib/server/db/types.ts` (an `import type` of the `db` singleton — so these modules never pull in `$env/dynamic/private` and can run from a standalone `tsx` script). Import `Database` from there; don't redeclare `typeof db` per module.
- `hashAuthCode` in `auth-codes.ts` is the **only** function allowed to hash a login code — the whole security property is that the request-code and verify-code paths hash identically, and a second copy of `createHash('sha256')...` that drifts would fail silently and permanently as "wrong code". US-B03 and any verification script must import it rather than re-inlining the one-liner. It's deliberately a plain SHA-256, not an HMAC: a 6-digit code has a 10^6 preimage space so the hash column is brute-forceable by anyone holding the table either way; the 10-minute TTL and 5-attempt cap are the real defense. Switching to a keyed HMAC later is a one-line change inside this function.
- Three invariants in those helpers that US-B02/B03/B05 must not undo: `incrementAuthCodeAttempts` does its arithmetic in SQL (a drizzle `sql` template on `authCodes.attemptCount`, not a JS read-modify-write) so parallel wrong-code submissions can't lose updates and walk past the 5-attempt lockout; `markAuthCodeUsed` carries an `isNull(usedAt)` guard making it an atomic compare-and-swap, so a returned `undefined` means "someone else already consumed this code" and the caller **must** reject rather than mint a session; and `invalidateActiveAuthCodes` supersedes codes by pulling `expires_at` back to now, **not** by setting `used_at` — so `used_at IS NOT NULL` always means "actually redeemed", and US-B03's error copy for a superseded code should say expired/no-longer-valid, not "already used".
- `src/lib/server/auth/verify-auth-sessions.mts` smoke-tests both modules against the **live** Turso DB (there is no separate test database); its body is wrapped in `try`/`finally` so inserted rows are cleaned up and the client closed even on an unexpected throw. Extend it rather than adding new ad hoc auth scripts.
- `/inbox` (`src/routes/(app)/inbox/+page.svelte`) is still an intentional placeholder pending the real inbox-list stories — don't be surprised it's an empty shell. `/login` is real as of US-B04 (see below).
- `.rodney/` (local rodney browser-automation state, created by `rodney --local`) is gitignored — don't commit it, and don't let a stray `npm run lint` failure from it confuse you; it should never show up in `git status` once `.gitignore` has the entry.
- `src/lib/server/auth/auth-codes.ts` and `src/lib/server/auth/sessions-store.ts` (US-B01) are the query helpers for the `auth_codes`/`sessions` tables — `createAuthCode`/`getActiveAuthCode`/`invalidateActiveAuthCodes`/`incrementAuthCodeAttempts`/`markAuthCodeUsed`/`deleteAuthCode`/`expireAuthCode`/`getLatestAuthCode`/`getAuthCodeRequestWindow` (US-B02/B04 rate-limit window stats)/`hashAuthCode`, and `createSession`/`getValidSessionByTokenHash`/`extendSessionExpiry`/`deleteSessionByTokenHash`. US-B02/US-B03/US-B05 should call these instead of writing new raw Drizzle queries. Each function takes the `db` handle as its first argument (typed via `import type { db as dbSingleton } from '../db'; type Database = typeof dbSingleton`) rather than importing the `db` singleton itself — this is a general pattern worth reusing for any future server module that needs both (a) real app code importing the actual `db` singleton and (b) a standalone `tsx` verification script building its own `drizzle(createClient(...))` instance from `process.env` (since `$env/dynamic/private` can't be imported outside Vite/SvelteKit). `import type` only pulls the type, not the module's runtime code, so this incurs no `$env` dependency. See `src/lib/server/auth/verify-auth-sessions.mts` for the pattern in action.
- `src/lib/server/email/resend.ts` (US-B02) wraps the `resend` npm package: `sendAuthCodeEmail(code)` sends the 6-digit login code to `getAuthRecipient()` (the `AUTH_RECIPIENT_EMAIL` env var, never request input — that's the FR-1 guarantee) from `auth@caseynazelrod.com`. Unlike `db`/`r2`, both env reads here are **lazy** (memoized client + per-call recipient lookup), not import-time: `npm run build` imports every `+server.ts` during its postbuild method-detection step, so an import-time `requireEnv` would make the build itself — and therefore CI and any fresh clone — require real or placeholder secrets. Deferring to the first send keeps the fail-fast behavior where it matters and keeps the build secret-free; prefer this shape over import-time env reads for any new server module reachable from a route. On a send failure it logs the provider's message server-side and throws a generic `Error`, so Resend's wording can never reach the client through an unhandled-error page. Future outbound-mail stories (US-H02) should add a general `sendEmail` helper alongside `sendAuthCodeEmail` in this same file rather than creating a second Resend client.
- `POST /api/auth/request-code` (`src/routes/api/auth/request-code/+server.ts`, US-B02) is the reference implementation for rate-limited request endpoints in this app: it checks `countAuthCodeRequestsSince` against a rolling window **before** doing any invalidate/insert/send, so a rate-limited (`429`) request never touches the DB write path or an external API. Follow this "check the limit first, side-effect after" ordering for any future rate-limited endpoint. The `429` carries both a `Retry-After` header and a `retryAfterMinutes` body field, and **both are derived from the same value** — `getAuthCodeRequestWindow` returns the window count and the oldest request's timestamp from one aggregate, the oldest being the row that next ages out. Keep them derived from one source; a header and a body that disagree about when to retry is worse than either alone. Set `Retry-After` on any future rate-limited response, not just the JSON body. If the Resend send throws, the endpoint deletes the just-created `auth_codes` row (`deleteAuthCode`) and returns a generic `502`: the plaintext code lives only in that request, so a row whose email never went out would leave the user with no valid code (the previous one was just superseded) _and_ burn one of their three requests per window. Any future "write a row, then call a third party that carries its only usable content" flow needs the same rollback.
- `POST /api/auth/verify-code` (`src/routes/api/auth/verify-code/+server.ts`, US-B03) always compares the submitted code against `getLatestAuthCode` (the single most-recently-created `auth_codes` row, any state), not `getActiveAuthCode` — this is what lets it tell apart "no code requested", "code already used", and "code expired" (each a distinct error message) from a genuine wrong-digits mismatch, and matters because attempts must **not** be incremented against a dead (used/expired) code. On a real digit mismatch it calls `incrementAuthCodeAttempts`; if that reaches 5 it kills the code with `expireAuthCode` — **not** `markAuthCodeUsed`, since a code burned by wrong guesses was never redeemed, and stamping `used_at` would make this endpoint's own already-used branch tell the user their code was "already used" when they never entered it correctly. On match it calls `markAuthCodeUsed` and **checks the return value**: `undefined` means a concurrent request carrying the same correct code already consumed it, and this one returns the already-used error instead of minting a second session. Then it generates an opaque 32-byte session token (`randomBytes(32).toString('hex')`), stores only its SHA-256 hash (via `hashSessionToken` in `sessions-store.ts` — deliberately a separate function from `hashAuthCode` despite the identical body, because the two hash different secrets with different threat models and keying one must not silently key the other) via `createSession`, and sets the raw token as the `session` cookie with `httpOnly`, `secure`, `sameSite: 'lax'` — mirrors the code-hashing pattern (raw value never persisted, only its hash). Any future code-comparison endpoint should use `timingSafeEqual` on equal-length hash buffers (see `hashesMatch` in that file) rather than `===`, to avoid a timing side-channel.
- `src/routes/login/+page.svelte` (US-B04) is the whole login flow in one page: a single "Send me a code" button that `POST`s to `/api/auth/request-code`, then an in-place transition (`step` state, not a second route) to a 6-digit code field that `POST`s to `/api/auth/verify-code` and `goto`s `/inbox`. **No email input field may ever appear here** — the recipient is the server-side `AUTH_RECIPIENT_EMAIL` constant (FR-1). Four conventions in it worth reusing:
  - The code field normalizes in `oninput` (`value.replace(/\D/g, '')`), not via a `pattern` attribute. `pattern` is inert on any form whose `onsubmit` calls `preventDefault()` and fetches manually — native constraint validation never runs. This also handles the `123 456`/`123-456` shapes people paste out of an email client.
  - The `role="alert"` error `<p>` is wrapped in `{#key errorNonce}`, with the nonce bumped every time an error is set. A live region whose new text is byte-identical to its old text is **not** re-announced, so two identical consecutive failures would otherwise be announced once. Do this for any repeated-error live region, not just this page.
  - `errorMessage` clears on input, so a stale failure doesn't sit on screen while the user is mid-correction.
  - It auto-submits once six digits are present (autofill delivers all six at once).
- There is deliberately **no `429` handling in the verify-code client path**: `/api/auth/verify-code` is not rate-limited — every rejection is a `400`. Brute force is bounded by the two limits that do exist (5 attempts per code, 3 codes per 10 minutes = at most 15 guesses per 10 minutes against a 10^6 space). If you find yourself writing a 429 branch there, add the server-side limit first or leave it out; a dead client branch for an impossible response is how the UI and server drift apart.
- A **real Resend API key is provisioned** in the local `.env` as of US-B04 — clicking "Send me a code" against a local dev server sends a real email to `AUTH_RECIPIENT_EMAIL`. Stub `/api/auth/request-code` in-page (`window.fetch`) when browser-testing steps that only need to reach the code-entry screen, and seed a known code hash directly into `auth_codes` instead.
- **All env vars are real and current in both the local `.env` and Vercel project settings** as of US-E01 (Turso, R2, Resend API key + recipient, and the inbound webhook secret). There are no placeholder credentials left in this project, and no outstanding credential-provisioning steps — if a future story hits an auth/credential failure, treat it as a real bug rather than assuming a stub value. `.env.example` documents every required name with empty values; the real ones live only in the gitignored `.env`.

## Design tokens (Dusk Terminal)

- All Dusk Terminal tokens (palette, fonts, radius scale, motion) live in `src/routes/layout.css`, using Tailwind v4's CSS-first `@theme` config — there is no `tailwind.config.js`/`.ts`.
- Palette: raw hex values are plain custom properties named `--dt-*` (e.g. `--dt-background`) set in `:root` (dark, the reference theme), overridden inside a `@media (prefers-color-scheme: light)` block scoped to `:root:not([data-theme])` (OS-default fallback), and again in `:root[data-theme='dark']` / `:root[data-theme='light']` (explicit user choice, always wins). The `@theme` block then maps Tailwind's color namespace onto these (`--color-background: var(--dt-background)`, etc.) so utilities like `bg-background`, `text-text-primary`, `border-border`, `text-accent`, `text-danger` are generated and theme-switch automatically. **Do not** set `--color-background: var(--color-background)` (self-reference) inside `@theme` — Tailwind's theme keys and the raw per-theme variables must have different names (`--dt-*` vs `--color-*`), or the custom property becomes CSS-invalid.
- Fonts: `@fontsource/inter` and `@fontsource/jetbrains-mono` are installed as real npm dependencies and imported directly in `layout.css` (`@import '@fontsource/inter/400.css';` etc., only the weights actually used: 400/500/600/700 for Inter, 400/500 for JetBrains Mono) — self-hosted, no external font CDN request at runtime. Exposed as `font-sans` (Inter) and `font-mono` (JetBrains Mono) Tailwind utilities. Per `tasks/prd-ui-ux.md` FR-2, monospace must be used for all metadata (timestamps, addresses, thread/message ids, the login code field), sans for everything else.
- Radius: the entire Tailwind radius namespace (`--radius-xs` through `--radius-full`, including `DEFAULT`/`--radius`) is overridden in `@theme` to values in the 2-4px range — this intentionally makes `rounded-full` non-pill-shaped in this app, matching the "no pill shapes, 2-4px everywhere" design rule. Don't add a new radius utility outside this scale.
- Motion: `--duration-fast` (120ms) / `--duration` (140ms) / `--duration-slow` (160ms) and `--ease-standard` (`cubic-bezier(0, 0, 0.2, 1)`, standard ease-out) are theme vars too, giving `duration-fast`/`duration`/`duration-slow` and `ease-standard` Tailwind utilities for all transitions. No bounce/spring easing per the design system.
- Theme toggle logic (not just CSS) lives in `src/lib/theme.svelte.ts`: `themeState` (a `$state` rune) tracks the explicit user choice (`'dark' | 'light' | null`, `null` = follow OS), `applyTheme`/`toggleTheme` set/clear the `data-theme` attribute on `<html>` and persist to `localStorage` (`dusk-terminal-theme` key). Call `initTheme()` once from the root `+layout.svelte` to sync `themeState` with `localStorage` on mount. `src/app.html` has a small inline (pre-hydration) script that reads the same `localStorage` key and sets `data-theme` before first paint, to avoid a flash of the wrong theme — keep that script and the `theme.svelte.ts` logic using the exact same storage key and value shape if either changes.
- `src/lib/components/ThemeToggle.svelte` is the reusable toggle button; `src/routes/dev/tokens/+page.svelte` is a dev-only page (unauthenticated, outside the `(app)` route group) that renders every token as a swatch/sample for visual QA — not part of the real app shell (that's US-J02), just a verification aid. Reuse this page rather than building a new one when adding future tokens.

## App shell

- `EmptyState` takes `message` (required) + optional `subCopy`; `Skeleton` takes `rows` (default 3) and renders that many pulsing `bg-surface` rows; `ErrorMessage` takes `message` (required) + optional `onRetry` and renders in `text-danger`, showing a Retry button only when `onRetry` is passed. All three are demoed on `/dev/tokens` under "Shared states" — extend that section (don't build a parallel demo page) when adding more shared components.
- Accessibility contract for these three: `Skeleton`'s pulse uses `motion-safe:animate-pulse` so it stops under `prefers-reduced-motion` (use `motion-safe:` for any future indefinite animation, not bare `animate-*`). `Skeleton` carries `role="status" aria-label="Loading"` itself, but **the consumer** is responsible for putting `aria-busy="true"` on the container whose content the skeleton is standing in for, and dropping it when real content arrives — do that in every consuming story (US-F01, US-G01, US-H01, US-I01) rather than inventing a per-caller convention. In `ErrorMessage`, `role="alert"` sits on the inner message `<span>`, not the flex wrapper, so the Retry button isn't read out as part of the alert announcement — keep live-region roles on the text node when a control sits beside it.
- When demoing/QAing a `bg-surface`-toned component (like `Skeleton`), wrap it in a `bg-background` container, not another `bg-surface` — same-tone nesting makes it visually disappear. Real usage in an actual list won't have this problem since the page background provides the contrast.
