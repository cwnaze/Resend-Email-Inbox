# Resend Email Inbox — Project Notes

## Stack

- SvelteKit (Svelte 5, runes mode forced via `vite.config.ts`'s `sveltekit({ compilerOptions: { runes: ... } })`), TypeScript, Tailwind CSS v4 (via `@tailwindcss/vite`, imported in `src/routes/layout.css` and pulled into `+layout.svelte`), `@sveltejs/adapter-vercel`.

## Gotchas

- This SvelteKit toolchain (current `sv create` output) configures the Vite plugin and the adapter directly in `vite.config.ts` — there is **no `svelte.config.js`** in this project. If you need to change adapter options or compiler options, edit `vite.config.ts`.
- `@sveltejs/adapter-vercel`'s runtime auto-detection only supports Node 20/22/24. If the local dev machine runs a newer Node (e.g. v26), `npm run build` fails with `Unsupported Node.js version` unless the adapter is given an explicit runtime. This is already set: `adapter({ runtime: 'nodejs22.x' })` in `vite.config.ts`. Don't remove it.
- `.prettierignore` excludes `/tasks/`, `/agents/`, and `/docs/demos/` — those are PRD/agent-process files and showboat demo logs, not app source, and are intentionally left unformatted by the app's prettier config.
- `docs/demos/<STORY_ID>.md` files are showboat proof-of-work logs (one per user story). When capturing command output in a showboat `exec` block for later `showboat verify` reproducibility, strip anything non-deterministic (timestamps, build durations, PIDs) with `grep`/`sed` before showboat records the output — otherwise `showboat verify` will fail on a re-run even though nothing is actually broken.

## Database (Turso / Drizzle)

- `src/lib/server/db/index.ts` exports `db`, a `drizzle-orm/libsql` client built from `TURSO_DATABASE_URL`/`TURSO_AUTH_TOKEN` read via `$env/dynamic/private` (not `$env/static/private` — keeps the module importable even in contexts where those vars aren't statically inlined). Only import this from server-only code (`+page.server.ts`, `+server.ts`, `src/lib/server/**`).
- `src/lib/server/db/schema.ts` is the single Drizzle schema file; `drizzle.config.ts` (repo root, `dialect: 'turso'`) points at it and at `./drizzle` for generated migrations.
- Full schema (since US-D01): `contacts`, `threads`, `emails`, `attachments`, `auth_codes`, `sessions`, per `tasks/prd-data-model.md`. Booleans are `integer({ mode: 'boolean' })`, JSON address-list columns are `text({ mode: 'json' })`, timestamps are `integer({ mode: 'timestamp_ms' })`. Declare indexes via the `sqliteTable(name, columns, (table) => [index(...), uniqueIndex(...)])` array-builder form (current drizzle-orm API), and FKs via `.references(() => otherTable.column)` on the column definition. FK enforcement is connection-dependent: a plain local SQLite connection needs `PRAGMA foreign_keys = ON` before it will _reject_ a violation, but the remote Turso connection these scripts open **does** enforce them (observed in US-E04: deleting a `threads` row before its `emails` rows fails with `SQLITE_CONSTRAINT`). So always delete children before parents, and don't assume a violation will pass silently. `src/lib/server/db/verify-schema.mts` is a standalone script (same `process.env`-reading, `tsx`-run pattern as `src/lib/server/r2/verify.mts`) that smoke-tests the live schema — extend it rather than writing new ad hoc scripts for future schema changes.
- Real Turso credentials live only in the gitignored root `.env` (never commit them); `.env.example` documents the variable names with empty values.
- `npm run db:push` applies the schema directly to the configured Turso database (no migration files); `npm run db:generate` emits SQL migration files under `./drizzle` if a versioned-migration workflow is needed later; `npm run db:studio` opens Drizzle Studio.
- Both `drizzle.config.ts` and `src/lib/server/db/index.ts` throw at startup if either `TURSO_DATABASE_URL` or `TURSO_AUTH_TOKEN` is missing — a remote Turso connection needs both, so failing fast on either avoids a confusing runtime error from `@libsql/client` later.
- If a future story switches to `npm run db:generate` (versioned migrations instead of `db:push`), commit the generated `./drizzle/*.sql` files and the `./drizzle/meta` journal — they're a source-of-truth migration history, not disposable build output, so `./drizzle` should NOT be gitignored once it's in use.

## Object storage (Cloudflare R2)

- `src/lib/server/r2/index.ts` exports three server-only utilities: `uploadToR2(key, body, contentType?)`, `deleteFromR2(key)`, and `getR2SignedDownloadUrl(key, expiresInSeconds?)` (default 15 min). Built on `@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner` against R2's S3-compatible API at `https://<R2_ACCOUNT_ID>.r2.cloudflarestorage.com`.
- The bucket is **private** — there is no `R2_PUBLIC_URL_BASE`/static public URL. Any place the app needs to let the browser fetch/download an object must call `getR2SignedDownloadUrl` on demand rather than storing a permanent URL. - Only import `src/lib/server/r2` from server-only code (`+page.server.ts`, `+server.ts`, `src/lib/server/**`) — same rule as the `db` client.

## Inbound webhook (Resend / Svix)

- `src/lib/server/webhooks/svix.ts` (US-E01) is the **only** place a webhook signature is verified: `verifySvixRequest(request)` reads `svix-id`/`svix-timestamp`/`svix-signature`, reads the body as **text**, and returns `{ ok: true, payload, rawBody } | { ok: false, reason }`. Three things to preserve:
  - It consumes the request body itself, as raw text. The Svix signature covers the exact bytes Resend sent, so `request.json()` followed by a re-serialize will not verify. A `Request` body can only be read once — callers must use the returned `payload`/`rawBody` and never call `request.json()` before or after.
  - `payload` exists only on the `ok: true` branch by construction, so US-E02..E05's ingestion code physically cannot reach an unverified body. Keep the result type discriminated rather than returning a payload plus a boolean.
  - `reason` is for `console.warn` server-side only. The endpoint returns a bare `401` with no detail — a failure reason tells an unauthenticated caller how to forge a better signature.
- The `RESEND_INBOUND_WEBHOOK_SECRET` read is **lazy** (memoized `Webhook` on first verify), not import-time, for the same reason as `email/resend.ts`: `npm run build` imports every `+server.ts` during method detection, so an import-time secret check would make the build require a real credential.
- `POST /api/webhooks/resend-inbound` (`src/routes/api/webhooks/resend-inbound/+server.ts`) is the gate; US-E02 onward hangs parsing/persistence off the verified `result.payload` inside it, and must not add a second parallel verification path.
- `src/lib/server/webhooks/verify-inbound-webhook.mts` smoke-tests the endpoint over HTTP against a running dev server (`WEBHOOK_BASE_URL`, default `http://localhost:5173`), using `svix`'s own `sign()` for the positive case. US-E02/E03 extended it to 14 checks by adding the full ingestion path against a real received email (see below), including the two status-code-contract cases: a non-`email.received` event and a permanently-unfetchable `email_id` both answered with `200`, not `500`. The load-bearing signature case is **tampered body + genuine signature → 401**: that's what proves the raw bytes are what's verified. Extend this script rather than adding new ad hoc webhook scripts.
- **Deployed and live** as of US-E01: the app is served from `https://mail.caseynazelrod.com` (Vercel, builds from `main`), the webhook is registered in the Resend dashboard against `POST https://mail.caseynazelrod.com/api/webhooks/resend-inbound`, and the real `whsec_…` secret is in both the local `.env` and Vercel project settings. Re-run the suite against production with `WEBHOOK_BASE_URL=https://mail.caseynazelrod.com node --env-file=.env node_modules/.bin/tsx src/lib/server/webhooks/verify-inbound-webhook.mts` (5/5 signature cases as of the US-E01 merge; 14/14 including the US-E02/E03 ingestion cases locally).
- DNS split worth knowing before touching domains: Resend owns `send.` (sending), `links.` (click tracking), and the **apex MX** (receiving); the app has the `mail.` subdomain to itself. So **inbound addresses are on the apex** — `something@caseynazelrod.com`, never `@mail.caseynazelrod.com`. Don't move the app onto a name that also holds MX records: Vercel wants a CNAME for a subdomain, and a CNAME must be the only record at its name, so it would block the MX outright (use an A record if that's ever unavoidable).
- Still unconfirmed as of US-E02: nothing has yet proven that a **real Resend delivery** reaches the deployed endpoint and passes `svix` verification. Apex MX receiving works (real inbound emails exist in the Resend account, and US-E02's parser was built against one), and the whole ingestion path is proven end-to-end locally against a real received email — but the signature leg is still this repo's own `sign()` hitting its own endpoint. Confirming it needs a real email plus a `200` for `/api/webhooks/resend-inbound` in the Vercel function logs.

## Inbound ingestion (parse + contacts)

- **The `email.received` webhook payload is metadata-only** — no body, no headers, no attachment content ("This design choice supports large attachments in serverless environments that have limited request body sizes"). This was confirmed against the real Resend account in US-E02 and it shapes all of US-E02..E05: `html`/`text`, the `From:` display name, `In-Reply-To`, `References` and the `Date:` header exist **only** on the fetched record. Ingestion is inherently two calls — verify the webhook, then `fetchReceivedEmail(email_id)` (`src/lib/server/email/resend.ts`, wrapping `resend.emails.receiving.get`). Attachment _content_ likewise needs the Attachments API (US-E05), not a base64 blob in the request body.
- Two quirks of the real fetched record, both pinned by fixtures in `verify-inbound-parse.mts`: Resend hands some header values back **JSON-encoded** (an observed delivery had `date: "\"2026-07-25T15:15:31.000Z\""`, `received: "[\"from …\"]"`), and header keys are lowercased. `headerValues()` in `parse.ts` decodes both encodings — a `"`-prefixed value to a single string, a `[`-prefixed one to a list (that's how a header occurring more than once comes back) — and falls back to the raw text when `JSON.parse` throws, so a display name like `"Google" <a@b>` survives untouched. `header()` is the single-value view (first entry). Multi-value headers must read `headerValues`, not `header`: `References` whitespace-split from an undecoded `["<id>"]` string would silently feed JSON punctuation into US-E04's threading.
- `parse.ts`'s `inboundMessageId` guarantees `ParsedInboundEmail.messageId` is **never empty** — an absent, null or blank `message_id` falls back to `<resend-{received.id}@inbound.invalid>`. `Message-ID` is optional in RFC 5322 and Resend does not validate it, and it is this app's idempotence key: an empty string would make `getEmailByMessageId('')` match the first such email and then silently drop every later one as a duplicate (mail lost behind a `200` — the worst failure this pipeline has), while a null would fail the `NOT NULL` insert and 500 forever against a permanent condition. The fallback uses Resend's own email id because it is unique per received email and stable across redeliveries, so idempotence still holds where it matters. Don't reintroduce a bare `received.message_id` read.
- The bare sender address is read from the record's own `from` field, **never** from `headers.from` — the header is only mined for the display name. A crafted `From:` must not be able to disagree with the envelope Resend actually validated. Keep that split if `parse.ts` grows.
- `src/lib/server/inbound/parse.ts` is pure by design (no env, no db, no network) so a standalone `tsx` script can exercise it against captured fixtures. Keep new parsing logic there rather than inside the `+server.ts`, and keep the fixture-based script (`src/lib/server/inbound/verify-inbound-parse.mts`) as the place US-E03/E04/E05 add parsing assertions.
- Endpoint status-code contract, worth preserving: **permanent** conditions return `200` with a server-side `console.warn` — a verified but unusable payload (wrong event type, missing `email_id`), _and_ a Received-emails fetch that fails with a 4xx (an `email_id` that is gone or inaccessible). Resend retries 5xx forever and none of those can start working. Only a **transient** failure (a 5xx/429/transport error from Resend, or the DB) is allowed to throw → `500`, which is exactly when a retry helps. `fetchReceivedEmail` encodes that split for the caller: it throws a `ReceivedEmailFetchError` carrying `retryable` (derived from `error.statusCode`) rather than a bare `Error`, so the endpoint doesn't have to re-classify provider errors itself. Getting this backwards either drops mail silently or builds an infinite retry loop.
- The endpoint's success `console.log` deliberately **omits the sender's email address** — it would write a real person's address into the platform's function logs on every delivery, and the `contact` id already identifies the row. Keep new inbound log lines id-only.
- `src/lib/server/inbound/sanitize.ts` (US-E03) is the **only** place inbound HTML is sanitized, and it runs on the **write** path: `sanitizeEmailHtml` is called by `storeInboundEmail` so what lands in `emails.body_html` is already safe and no renderer downstream can forget to re-sanitize. Never persist Resend's raw `html`. It's `isomorphic-dompurify` with an explicit `FORBID_TAGS`/`FORBID_ATTR` list on top of the defaults (`iframe`/`link`/`style`/`form`/`svg`…, plus `srcset`/`background`/`ping`/`style`/`formaction`) — DOMPurify already strips `script` and every `on*` handler, but a default is a thing that can change under us and a mail client leaking a read receipt via `<iframe>`/`<link>` is exactly the threat here. A blank or entirely-malicious body sanitizes to `null`, not `''`, so the column stays NULL. `body_text` is stored verbatim: it is never rendered as markup.
- `src/lib/server/inbound/store.ts`'s `storeInboundEmail` is the persistence step (parse → sanitize → insert), and `src/lib/server/db/emails.ts` holds the `emails`/`threads` query helpers (db-handle-first, same as `contacts.ts`). Idempotence on `message_id` (FR-2) is enforced **twice on purpose**: a cheap `getEmailByMessageId` read up front so a redelivery never creates an orphan `threads` row, and `insertInboundEmail`'s `onConflictDoNothing()` + re-read as the authority underneath for two genuinely concurrent deliveries. Only the index can win that race; only the read can avoid the litter — and when the read misses but the index catches it, the thread just created is deleted again. US-E04 replaces the _choice_ of thread inside `storeInboundEmail` (In-Reply-To / subject matching) but not this structure.
- Thread assignment, the email insert and the thread touch run inside **one `db.transaction`**. This is load-bearing in both directions and must not be unwound into sequential calls: a failure _after_ the insert would leave a stored email whose thread still reads as read with a stale `last_message_at`, and because the up-front duplicate check short-circuits, Resend's redelivery returns early and never repairs it — the message is stranded out of the inbox sort order permanently. Rolling back also means a failed insert takes its just-created thread with it, so no best-effort cleanup path can get it wrong. Because the thread row is still uncommitted, the duplicate branch's `deleteThread` also can't hit an FK violation from a concurrent delivery attaching to it. `Database` in `src/lib/server/db/types.ts` is therefore a **union of the singleton and a transaction handle**, which is what lets every query helper run unchanged on either.
- `src/lib/server/db/contacts.ts` owns the `contacts` table (db-handle-first, same pattern as the auth helpers). Three invariants: addresses are stored **lowercased** (`normalizeEmail`) because `contacts_email_unique` is a plain case-sensitive SQLite index and that normalization is what makes it enforce one row per address, while reads still compare with `lower()`; the insert uses `onConflictDoNothing()` + a re-read so a concurrent redelivery of the same email is a no-op rather than a 500; and a contact with `auto_created = false` has been **hand-edited by the owner** (US-I02) so its name is never overwritten by an inbound display name. An `auto_created = true` contact does get its name refreshed, since a later delivery carrying a display name beats the null a bare-address delivery left behind.

### Threading (US-E04)

- `src/lib/server/inbound/threading.ts` owns `normalizeSubject` (strips stacked `Re:`/`Fwd:`/`Aw:`/`Sv:`… prefixes, including `Re[2]:`, collapses whitespace, lowercases) and `SUBJECT_THREAD_WINDOW_MS` (30 days, FR-4). Pure, like `parse.ts`.
- **`threads.subject` stores the normalized subject; `emails.subject` keeps the sender's original wording.** The normalized column is the grouping key for the subject fallback, so writing a raw `Re: …` into it would silently stop that thread from ever matching again. Anything rendering a thread header (US-F01/G01) should expect a lowercased, prefix-stripped string and may prefer the newest email's own subject.
- `assignThread` in `inbound/store.ts` is the single place a thread is chosen, in this order: `In-Reply-To`, then the `References` chain **nearest-ancestor-first** (so a reply whose direct parent this mailbox never received still threads), then the 30-day same-normalized-subject fallback, then a new thread. Headers beat the heuristic; never reorder that.
- Never let an **empty** normalized subject match the fallback — every subject-less email in the mailbox would collapse into one thread. `findThreadBySubject` returns early on `''`.
- Per the Data Model PRD, `threads.is_read` means "every message in the thread is read", so `touchThreadForNewMessage` forces it back to `false` on arrival, and `last_message_at` **only moves forward** — a late redelivery of an older message must not drag a thread down the inbox sort order. That comparison is a SQL `max()` inside the `UPDATE`, not a JS read-modify-write (same reason as `incrementAuthCodeAttempts`): two messages landing in one thread concurrently would otherwise interleave select-then-update and let the older timestamp win.
- `storeInboundEmail` takes an injectable `now` (default `new Date()`) purely so the 30-day window is testable, and returns `threadMatch: 'reply' | 'subject' | 'new' | 'duplicate'` for the endpoint's log line. A thread the call _created_ is deleted again if the email turns out to be a duplicate; a thread it merely _joined_ is left alone.

### Attachments (US-E05)

- `src/lib/server/inbound/attachments.ts` owns inbound attachment extraction; `src/lib/server/db/attachments.ts` is the `attachments` table's query helper (db-handle-first, like `emails.ts`). Attachment bytes are never written to a DB column (FR-5) — only `r2_object_key`.
- The two provider hops (`fetchReceivedAttachmentBytes` in `email/resend.ts`, `uploadToR2`) are **injected** into `storeInboundAttachments` as a `deps` object rather than imported, because both of those modules read env — that's what keeps this module runnable from the standalone `tsx` verification script with stubs, same as `parse.ts`/`store.ts`. The endpoint wires the real implementations.
- Resend's Attachments API returns a short-lived signed `download_url`, not the bytes; `fetchReceivedAttachmentBytes` does both hops and deliberately never returns or persists that URL — it expires, and the app's own download links are presigned from R2 on demand.
- If the upload succeeds but the `attachments` insert then fails, the just-uploaded object is deleted again via the optional `remove` dep (`deleteFromR2`): nothing would reference it and the email's duplicate check means no redelivery ever repairs it, so without the undo the bucket accumulates unreachable blobs. A failure of the delete itself is only logged.
- Per-attachment failures are **swallowed and logged**, never thrown: the email row is already committed and acknowledged, so a throw would make Resend redeliver a message whose duplicate check short-circuits — the retry couldn't repair the attachment and every attempt would be a 500 no-op. A retry-later state is out of scope for v1.
- Attachments are processed **sequentially** (bounded peak memory in a serverless function), only when `storeInboundEmail` reports `created` (a redelivery's bytes are already in R2 under the same key), and `size_bytes` comes from the downloaded bytes rather than the reported metadata size (metadata can describe the transfer-encoded size).
- The R2 key is `inbound/<resend_email_id>/<attachment_id>[-<slugified filename>]`. Resend's attachment id — not the filename — is what makes it unique: two attachments on one email can share a name, and a sender-supplied string must never decide where an object lands. `attachmentFilename` reduces a nullable, sender-controlled filename to one path segment (no traversal), strips control bytes, and falls back to `attachment-<id>`.
- Cleanup order in any script that deletes inbound rows: **attachments → emails → threads**. The remote Turso connection enforces the `attachments.email_id` FK, so deleting emails first throws `SQLITE_CONSTRAINT`.

## Inbox list (US-F01)

- `src/lib/server/db/inbox.ts`'s `listInboxThreads` is the inbox list query and is deliberately **one** query (FR-1, no per-row N+1): the preview columns come from a correlated subquery picking each thread's latest `is_deleted = 0` email, joined with `innerJoin`. That inner join is load-bearing twice — it supplies the preview _and_ it is what excludes threads whose every member email is soft-deleted. Don't add a separate `NOT EXISTS` for the soft-delete rule; two expressions of "visible email" can drift apart. Ordering is `last_message_at desc, id desc` (the id breaks ties deterministically so a row can't swap places between loads).
- `src/lib/inbox/format.ts` holds `bodySnippet` / `senderLabel` / `relativeTime` and is **pure** (no env, no db, no DOM) so the server load, the Svelte components and a standalone `tsx` script all import the same code — same rationale as `inbound/parse.ts`. `bodySnippet`'s HTML de-tagging is **not** a sanitizer and its output is only ever inserted as text; inbound HTML is already sanitized on the write path. Snippets are derived in the load, not the component, so a large HTML body never crosses the wire just to render one preview line.
- `relativeTime` renders a future timestamp as "now" rather than a negative duration — the sender's `Date:` header can be ahead of this machine's clock.
- **`resolve()` needs the route id including the route group for a dynamic route**: `resolve('/(app)/inbox/[threadId]', { threadId })`, not `'/inbox/[threadId]'` (that only typechecks for static routes). The generated union of valid ids is in `.svelte-kit/non-ambient.d.ts`.
- `svelte/no-unused-props` is on, so don't declare a prop now for a later story to style — use it or leave it out.
- `src/routes/(app)/inbox/[threadId]/` is the real thread view as of US-G01 (see its own section below); the placeholder page US-F01 stood up there is gone.

### Read/unread filter (US-F03)

- `src/lib/inbox/filter.ts` is the single definition of the filter: `INBOX_FILTERS` (`all | unread | read`), `INBOX_FILTER_PARAM`, `parseInboxFilter` and `inboxFilterSearch`. Pure, like `format.ts`. `parseInboxFilter` **falls back to `all`** for anything unrecognised rather than erroring — the filter is a view preference, and a 400 on a hand-edited or stale query string would turn a bookmark into a broken inbox.
- `inboxFilterSearch` builds the link's query string from the **current** `URLSearchParams`, so US-F04's `?q=` survives a filter change (FR-3 requires both to be representable at once). `all` deletes the param instead of writing `?filter=all`. Any future list-state param should go through this function rather than rebuilding the query string.
- The narrowing happens in `listInboxThreads` (`filter` option → a `where` on `threads.isRead`), i.e. server-side per FR-2's spirit — never by hiding rows the client already received. It filters the **thread-level** flag ("every message in the thread is read"), not the previewed email's, so it agrees with the unread dot by construction.
- `src/lib/server/db/inbox.ts` imports the filter type by **relative** path, not `$lib/...`: `verify-inbox-list.mts` loads that module under plain `tsx`, which has no Vite alias resolution. Same constraint applies to anything else `inbox.ts` starts importing.
- `svelte/no-navigation-without-resolve` inspects the `href` **attribute expression**, so `FilterTabs.svelte` writes `href="{resolve('/(app)/inbox')}{link.search}"` inline; precomputing a full href in a `$derived` and passing it down fails lint. Derive only the query string.
- The filter tabs use `aria-current="true"`, not `"page"` — all three links address the same page. The empty state's copy is per-filter, since "New mail will show up here" is wrong when the mail exists and is merely filtered out.
- `src/lib/server/db/seed-f03-demo.mts` seeds a read thread, an unread thread and a `123456` login code for browser demos and removes them with `--cleanup`; it deletes its own rows before inserting so it is re-runnable (`message_id` is unique). Reuse it for US-F04/G01 browser verification rather than seeding by hand.

### Subject/sender search (US-F04)

- `src/lib/inbox/params.ts`'s `withListParam(current, param, value)` is now the **single** place an inbox list-state query string is built — `inboxFilterSearch` and `inboxSearchSearch` are both thin wrappers over it. FR-3 needs `?filter=` and `?q=` to coexist, which only holds if every control edits its own param and copies the rest; add a third list param here rather than assembling a query string at a call site.
- `src/lib/inbox/search.ts` owns `INBOX_SEARCH_PARAM` (`q`), `MAX_INBOX_QUERY_LENGTH` (200) and `parseInboxQuery` (collapse whitespace → trim → cap). Pure, like `filter.ts`. A whitespace-only or absent `?q=` must normalize to `''`, and `''` must never reach the query: a `%%` pattern matches every thread, so the list would look unfiltered while the UI claims a search is active. `listInboxThreads` re-runs `parseInboxQuery` on its own `query` option for that reason — it does not trust the caller.
- The match itself is `inboxSearchCondition` in `src/lib/server/db/inbox.ts`, inside the **same single query** as the rest of the list (FR-1) and before the `limit` — a post-filter in JS would search one page rather than the mailbox. Subject side compares `lower(threads.subject)` (already the normalized subject, which is why "invoice" finds "Re: Invoice #4"); sender side is an `exists` subquery over the thread's **non-deleted** emails, so a reply from the person searched for matches even when it isn't the previewed message, and a soft-deleted email can't pull in a thread with nothing on screen to explain the hit.
- `inboxSearchLikePattern` lowercases and escapes `%`, `_` and `\`, and every use of the pattern carries `escape '\'`. Don't lean on SQLite's own `LIKE` case-insensitivity (ASCII-only, and `PRAGMA case_sensitive_like` can flip it), and don't drop the escaping — an unescaped `%` typed by the user matches everything.
- `src/routes/(app)/inbox/SearchBox.svelte` is a plain `method="GET"` form, no JS: submitting navigates to `?q=…`. Because a GET submit **replaces the whole query string** with the form's own fields, the active filter rides along as a hidden input — without it, searching would silently reset the view to All. Submitting an empty box therefore leaves a bare `?q=` in the URL (harmless: it parses to "no search"); the `Clear` link is the affordance that actually drops the param, since it goes through `inboxSearchSearch`.
- US-J02's top-bar placeholder search input is **gone** from `(app)/+layout.svelte`. Search belongs to the inbox subtree for the same reason the placeholder thread list left the shell in US-F01: a `/contacts` page would otherwise inherit a box that searches a list it isn't showing.

### Unread treatment (US-F02)

- `markThreadRead` in `src/lib/server/db/emails.ts` is the only place read state is cleared: it marks every email in the thread read, then **recomputes** `threads.is_read` with a `not exists` over the thread's non-deleted unread emails, both inside one transaction. Never replace that recompute with a blind `set({ isRead: true })` — an inbound message can land between the two statements (`touchThreadForNewMessage` sets the thread unread) and the blind write would hide a message the owner never saw. Soft-deleted emails are marked read but don't count toward the thread flag, otherwise a deleted-but-unread email pins the thread unread with nothing visible on screen to explain it.
- `src/app.html` sets `data-sveltekit-preload-data="hover"` app-wide, so **any link whose load has a side effect must opt down** — `ThreadRow.svelte` sets `data-sveltekit-preload-data="tap"` because hovering the list would otherwise mark rows read. Keep that in mind for any future mutating load (or move the mutation to a form action).
- The unread dot is `rounded-[50%]`, not `rounded-full`: the radius namespace is capped at 2-4px app-wide, so `rounded-full` is a barely-rounded square here. Its gutter keeps its width on read rows so the text doesn't shift when a thread is opened. The dot is `aria-hidden` with an `sr-only` "Unread." beside it — state must not be colour-only.
- The `(app)` shell no longer has the placeholder 360px left column US-J02 stood up: a thread list belongs to the inbox subtree, not to every `(app)` route (a `/contacts` page would have inherited an inbox list beside it). **US-G01 did not reintroduce the list/detail split** either — see the thread-view section below for why it is blocked on the mark-read ordering; both the list and the thread view render full-width in the shell's pane, each capped at `max-w-3xl`.
- `src/lib/server/db/verify-inbox-list.mts` is the standalone check (pure helpers on fixtures + `listInboxThreads` against the live DB, seeded rows deleted in `finally`). Extend it for US-F02/F03/F04 rather than adding new ad hoc scripts.
- Browser-verifying a page behind the httpOnly session cookie: `document.cookie` **cannot** set it (that's how US-J02's demo faked one, and it no longer works for a real session). Seed an `auth_codes` row with `hashAuthCode('123456')`, then from the page run `fetch('/api/auth/verify-code', { method: 'POST', body: JSON.stringify({ code: '123456' }) })` — the browser applies the endpoint's own `Set-Cookie`. No need to drive the login UI or stub `window.fetch`.

## Thread view (US-G01)

- `src/lib/server/db/emails.ts`'s `listThreadEmails` is the thread's read query: non-deleted emails only, `received_at asc` with `id` as the tie-breaker (the sort key is a sender-supplied `Date:` header, so two messages can share a millisecond). Excluding soft-deleted rows _in the query_ is what makes "no visible messages" a `length === 0` answer the load can 404 on, using the same definition of "visible email" as `listInboxThreads`' inner join — don't reintroduce a separate filter in the load.
- `src/routes/(app)/inbox/[threadId]/+page.server.ts` 404s twice: unknown thread id, and a thread whose every message is soft-deleted. The second check runs **before** `markThreadRead`, so a navigation that can't render anything doesn't mutate read state on the way out. `src/routes/(app)/inbox/[threadId]/+error.svelte` is the boundary that renders both (route-scoped, so the copy can say "this thread" and offer the one useful action — back to the list).
- The header shows the **newest message's own `subject`**, never `threads.subject`: that column holds the normalized grouping key (lowercased, `Re:`-stripped). Any future thread-titled UI should do the same.
- Body rendering is decided **in the load**, not the component (same reason the list derives snippets server-side): US-G02 replaced the plain-text-only rendering with two mutually exclusive branches — see the HTML-rendering section below. `bodyPlainText`/`htmlToPlainText` are still what a text-only message renders through, and are explicitly not sanitizers; nothing in this view uses `{@html}`.
- New pure helpers in `src/lib/inbox/format.ts` (still no env/db/DOM, still shared by the load, the components and `verify-inbox-list.mts`): `bodyPlainText` (text body preferred, de-tagged HTML fallback — the same precedence as `bodySnippet`, so a row's preview and the message it opens can't derive from different halves of the row), `htmlToPlainText` (collapses horizontal whitespace, keeps line structure, caps blank runs at one), `addressListLabel` (null/empty/blank-only all collapse to `''` so the component renders no `cc` line rather than a dangling label), and `absoluteTime`. `decodeBasicEntities` decodes `&amp;` **last** — decoding it first double-decodes `&amp;lt;`.
- **The list/detail split is still not built, and it isn't just layout work.** A `+layout.server.ts` load runs _in parallel_ with the page load it wraps, so an inbox list living in `inbox/+layout.svelte` would render from a snapshot taken before the thread page's `markThreadRead` committed: the row just opened keeps its unread dot until some later navigation. Building the split means moving the mark-read mutation to a form action or adding an explicit invalidation first — which is US-G04's territory.
- `svelte/no-unused-props` also rejects a declared prop field a component never reads, not just an unused prop: `ThreadMessage`'s `Props` deliberately omits the `id` its parent uses as the `#each` key.
- `src/lib/server/db/seed-f03-demo.mts` (despite the F03 name) is the shared browser-demo seeder: read thread, unread thread, a three-message conversation (HTML-only second message carrying one remote and one `data:` image for US-G02's toggle, `cc`, soft-deleted third) and a `123456` login code. `--hide-conversation` soft-deletes the conversation's messages to demo the empty-thread 404; `--cleanup` removes everything. It prints **no row ids** on purpose — a demo that pasted a generated UUID into a URL couldn't be re-run by `showboat verify`, so reach the thread by searching the list and clicking the row.

### HTML rendering and remote images (US-G02)

- The thread view has exactly **two** body branches and never both: `message.html` non-null → `EmailHtmlBody.svelte` (a sandboxed `<iframe srcdoc>`); otherwise the plain-text `<pre>`. HTML **wins** when a message has both bodies — the opposite precedence from `bodySnippet`/`bodyPlainText`, which prefer text because a _preview_ wants the cheapest readable form, not the richest. Don't "unify" the two precedences.
- That preference is qualified by `htmlHasVisibleText` (in `format.ts`) and the qualifier is **load-bearing**: a transactional email whose HTML part is a hidden preheader plus a 1×1 tracking pixel sanitizes to non-empty markup that renders **blank**, so preferring HTML unconditionally replaced a readable text body with an empty frame and a "1 remote image blocked" notice — the message unreachable. When the HTML has no text of its own _and_ there is no text alternative, HTML still wins (an image-only newsletter has nothing else to show). `src/lib/server/db/seed-g02-pixel.mts` is that fixture, deliberately its own thread because US-G01's demo asserts its conversation renders exactly two messages.
- `src/lib/inbox/srcdoc.ts` is pure (no env/db/DOM/**dependencies**) and owns `BLOCKED_IMAGE_ATTR`, `restoreBlockedImages` and `buildEmailSrcdoc`; `src/lib/server/inbox/html.ts` owns `prepareEmailHtml`, the server-only half (it pulls in DOMPurify). The split is what lets the component build the document without shipping DOMPurify to the browser, and lets `verify-inbox-list.mts` exercise both under bare `tsx` — so `server/inbox/html.ts` imports by **relative** path, same constraint as `server/db/inbox.ts`.
- **Image blocking is a read-path pass, not a write-path one.** `emails.body_html` keeps the sender's image URLs: "Load images" has to be able to put them back, and FR-3 wants the opt-in _per message_, which a stored-once-stripped body could not offer. So `prepareEmailHtml` runs on every thread load and returns `{ html, blockedImageCount }`.
- The parked URL lives on a `data-*` attribute **because** `SANITIZE_OPTIONS` sets `ALLOW_DATA_ATTR: false`: a sender who writes `data-dt-blocked-src` themselves has it stripped before this pass adds ours, so the only values that can ever be restored to `src` are the ones this app moved. Keep those two facts together — allowing data attributes would turn the restore step into a sender-controlled image loader. For the same ordering reason a `javascript:` src is already gone (DOMPurify's URI allow-list runs first), so parking can never reintroduce a scheme the sanitizer refused.
- `SANITIZE_OPTIONS` is exported from `src/lib/server/inbound/sanitize.ts` and shared by both paths, so a row written before that module existed can't be rendered under weaker rules than one written after. `prepareEmailHtml` re-sanitizing is deliberate, not redundant.
- `prepareEmailHtml` uses `RETURN_DOM_FRAGMENT` and walks the fragment — **not** a DOMPurify `afterSanitizeAttributes` hook. Hooks live on the process-wide DOMPurify singleton, and `removeHook(entryPoint)` pops whichever hook is _last_ rather than a named one, so once any second hook exists anywhere in the process the cleanup can remove the wrong one and leave this closure installed on the **write** path — quietly writing `data-dt-blocked-src` into stored bodies. The hook version was also only correct while nothing `await`ed between add and remove. Don't reintroduce it. (Fragment mode was checked byte-identical to string mode across the adversarial fixtures.)
- `data:` and `cid:` sources are never counted as blocked (bytes already present / a reference that reaches nobody) — counting them would show a "Load images" button that can't do anything. Remote `src`/`poster` on `video`/`audio`/`source`/`track` is dropped outright with no restore affordance: the story asks for an image opt-in, not a media one.
- The toggle is enforced **twice**: the attribute swap _and_ the srcdoc's CSP `<meta>` (`default-src 'none'`, `img-src data:` until the reader opts in). Keep both — the CSP is what still holds if some future markup path sneaks a `src` past the blocking pass.
- `sandbox="allow-same-origin"` with **no** `allow-scripts` is the containment. `allow-same-origin` is there so the parent can read `contentDocument` — to size the frame and to intercept link clicks; since scripting is off inside, nothing in there can use the shared origin.
- **A sandbox without `allow-popups` does not make links inert.** A plain `<a href>` navigates the frame _itself_, which sandbox always permits — verified in a browser: the remote page rendered inside the app's chrome and the frame went cross-origin, which also silently killed the height measurement. What prevents it is the srcdoc's **`<base target="_blank">`**: opening a new context is exactly what the sandbox blocks, so the worst case is "nothing happens", declaratively, before hydration and even if hydration never runs. `EmailHtmlBody`'s `interceptLinkClick` is the _upgrade_ (a real new tab via `window.open(..., 'noopener')`), never the guarantee — don't delete the `<base>` on the grounds that the handler covers it.
- That handler's element check is **duck-typed, not `instanceof Element`**: the frame is its own realm, so `instanceof` against this document's `Element` is always false for nodes from inside the frame and the guard swallows every click — which looks like working code and silently restores the takeover. (This bit once already.)
- **Height comes from the body box, never `documentElement.scrollHeight`.** The root's scroll height is floored at the frame's own viewport height, i.e. it reports back whatever height was last set: the frame could then only grow, never shrink, and short messages were padded to the initial guess. The srcdoc body also sets `display: flow-root` so the last child's bottom margin is _inside_ the measured box — without it `body.scrollHeight` stops above the final line and the frame clips it. Measure on `load`, re-measure with a `ResizeObserver` on the body (an image finishing after `load` is the common case), and also measure from an `$effect` when `readyState` is already `complete`: on a server-rendered page the srcdoc can finish loading before hydration attaches `onload`, and `load` fires once.
- The iframe document is forced light-on-white regardless of the app theme: email HTML brings its own colours and assumes a light canvas, so a dark one yields dark-on-dark text. The blocked-image placeholder is styled via an `img[data-dt-blocked-src]` **attribute selector**, so restoring `src` removes the placeholder styling by construction — no second marker to remember to strip.

## Auth / route protection

- Every mailbox route lives under the `src/routes/(app)/` route group. `src/routes/(app)/+layout.server.ts` is the single choke point: it calls `validateSession(db, cookies)` and redirects to `/login` on `null`. Add new protected pages under `(app)/` and they inherit this automatically — no per-route auth code needed, and never a second parallel check.
- `src/lib/server/auth/session.ts` (real as of US-B05) owns the session **cookie**, as distinct from `sessions-store.ts` which owns the `sessions` **table**: `SESSION_COOKIE_NAME`, `SESSION_TTL_MS` (30 days, FR-9), `setSessionCookie`/`clearSessionCookie`, `validateSession(db, cookies, now?)` (hash the cookie token → look up the row → reject missing/unknown/expired), and `destroySession(db, cookies)` (delete the row + clear the cookie). Four things to preserve here:
  - The cookie's name and its `path`/`httpOnly`/`secure`/`sameSite` flags are defined **once** in this module, and both `verify-code` (set) and `logout` (delete) go through the helpers. `cookies.delete` with a different `path` than the cookie was set with silently does not delete it, so re-specifying the options at a call site is a real bug waiting to happen — don't.
  - `validateSession` returns plain `null` for missing, unknown, _and_ expired cookies. Distinguishing them for the caller would leak whether a given token ever existed, and route protection treats all three the same anyway.
  - Sliding expiration (FR-9) only writes once the session is past the halfway point of its TTL, not on every request — a per-page-view DB write buys nothing, and refreshing at the halfway mark still means anyone active within any 15-day span never expires. When it does refresh, it re-sets the cookie so the browser's copy matches the row.
  - `(app)/+layout.server.ts` clears the cookie before redirecting, so a stale token isn't re-sent on every subsequent request.
- `POST /api/auth/logout` (`src/routes/api/auth/logout/+server.ts`, US-B05) deletes the `sessions` row and clears the cookie, then `303`s to `/login` (303 so the browser follows with a GET — the app shell's logout control is a plain JS-free `<form method="POST">`). Deleting the row is the whole point of FR-8: clearing only the cookie would leave a live row that a copied token could still use. It lives under `/api/auth/` alongside `request-code`/`verify-code` — the old `/logout` route from US-J02 is gone.
- `src/lib/server/auth/auth-codes.ts` and `src/lib/server/auth/sessions-store.ts` (US-B01) are the Drizzle query helpers for the `auth_codes`/`sessions` tables. Each takes the db handle as its first argument, typed as `Database` from `src/lib/server/db/types.ts` (an `import type` of the `db` singleton — so these modules never pull in `$env/dynamic/private` and can run from a standalone `tsx` script). Import `Database` from there; don't redeclare `typeof db` per module.
- `hashAuthCode` in `auth-codes.ts` is the **only** function allowed to hash a login code — the whole security property is that the request-code and verify-code paths hash identically, and a second copy of `createHash('sha256')...` that drifts would fail silently and permanently as "wrong code". US-B03 and any verification script must import it rather than re-inlining the one-liner. It's deliberately a plain SHA-256, not an HMAC: a 6-digit code has a 10^6 preimage space so the hash column is brute-forceable by anyone holding the table either way; the 10-minute TTL and 5-attempt cap are the real defense. Switching to a keyed HMAC later is a one-line change inside this function.
- Three invariants in those helpers that US-B02/B03/B05 must not undo: `incrementAuthCodeAttempts` does its arithmetic in SQL (a drizzle `sql` template on `authCodes.attemptCount`, not a JS read-modify-write) so parallel wrong-code submissions can't lose updates and walk past the 5-attempt lockout; `markAuthCodeUsed` carries an `isNull(usedAt)` guard making it an atomic compare-and-swap, so a returned `undefined` means "someone else already consumed this code" and the caller **must** reject rather than mint a session; and `invalidateActiveAuthCodes` supersedes codes by pulling `expires_at` back to now, **not** by setting `used_at` — so `used_at IS NOT NULL` always means "actually redeemed", and US-B03's error copy for a superseded code should say expired/no-longer-valid, not "already used".
- `src/lib/server/auth/verify-auth-sessions.mts` smoke-tests both modules against the **live** Turso DB (there is no separate test database); its body is wrapped in `try`/`finally` so inserted rows are cleaned up and the client closed even on an unexpected throw. Extend it rather than adding new ad hoc auth scripts.
- `/inbox` (`src/routes/(app)/inbox/+page.svelte`) is still an intentional placeholder pending the real inbox-list stories — don't be surprised it's an empty shell. `/login` is real as of US-B04 (see below).
- `.rodney/` (local rodney browser-automation state, created by `rodney --local`) is gitignored — don't commit it, and don't let a stray `npm run lint` failure from it confuse you; it should never show up in `git status` once `.gitignore` has the entry.
- `src/lib/server/auth/auth-codes.ts` and `src/lib/server/auth/sessions-store.ts` (US-B01) are the query helpers for the `auth_codes`/`sessions` tables — `createAuthCode`/`getActiveAuthCode`/`invalidateActiveAuthCodes`/`incrementAuthCodeAttempts`/`markAuthCodeUsed`/`deleteAuthCode`/`expireAuthCode`/`getLatestAuthCode`/`getAuthCodeRequestWindow` (US-B02/B04 rate-limit window stats)/`hashAuthCode`, and `createSession`/`getValidSessionByTokenHash`/`extendSessionExpiry`/`deleteSessionByTokenHash`. US-B02/US-B03/US-B05 should call these instead of writing new raw Drizzle queries. Each function takes the `db` handle as its first argument (typed via `import type { db as dbSingleton } from '../db'; type Database = typeof dbSingleton`) rather than importing the `db` singleton itself — this is a general pattern worth reusing for any future server module that needs both (a) real app code importing the actual `db` singleton and (b) a standalone `tsx` verification script building its own `drizzle(createClient(...))` instance from `process.env` (since `$env/dynamic/private` can't be imported outside Vite/SvelteKit). `import type` only pulls the type, not the module's runtime code, so this incurs no `$env` dependency. See `src/lib/server/auth/verify-auth-sessions.mts` for the pattern in action.
- `src/lib/server/email/resend.ts` (US-B02) wraps the `resend` npm package: `sendAuthCodeEmail(code)` sends the 6-digit login code to `getAuthRecipient()` (the `AUTH_RECIPIENT_EMAIL` env var, never request input — that's the FR-1 guarantee) from `auth@caseynazelrod.com`. Unlike `db`/`r2`, both env reads here are **lazy** (memoized client + per-call recipient lookup), not import-time: `npm run build` imports every `+server.ts` during its postbuild method-detection step, so an import-time `requireEnv` would make the build itself — and therefore CI and any fresh clone — require real or placeholder secrets. Deferring to the first send keeps the fail-fast behavior where it matters and keeps the build secret-free; prefer this shape over import-time env reads for any new server module reachable from a route. On a send failure it logs the provider's message server-side and throws a generic `Error`, so Resend's wording can never reach the client through an unhandled-error page. Future outbound-mail stories (US-H02) should add a general `sendEmail` helper alongside `sendAuthCodeEmail` in this same file rather than creating a second Resend client.
- `POST /api/auth/request-code` (`src/routes/api/auth/request-code/+server.ts`, US-B02) is the reference implementation for rate-limited request endpoints in this app: it checks `countAuthCodeRequestsSince` against a rolling window **before** doing any invalidate/insert/send, so a rate-limited (`429`) request never touches the DB write path or an external API. Follow this "check the limit first, side-effect after" ordering for any future rate-limited endpoint. The `429` carries both a `Retry-After` header and a `retryAfterMinutes` body field, and **both are derived from the same value** — `getAuthCodeRequestWindow` returns the window count and the oldest request's timestamp from one aggregate, the oldest being the row that next ages out. Keep them derived from one source; a header and a body that disagree about when to retry is worse than either alone. Set `Retry-After` on any future rate-limited response, not just the JSON body. If the Resend send throws, the endpoint deletes the just-created `auth_codes` row (`deleteAuthCode`) and returns a generic `502`: the plaintext code lives only in that request, so a row whose email never went out would leave the user with no valid code (the previous one was just superseded) _and_ burn one of their three requests per window. Any future "write a row, then call a third party that carries its only usable content" flow needs the same rollback.
- `POST /api/auth/verify-code` (`src/routes/api/auth/verify-code/+server.ts`, US-B03) always compares the submitted code against `getLatestAuthCode` (the single most-recently-created `auth_codes` row, any state), not `getActiveAuthCode` — this is what lets it tell apart "no code requested", "code already used", and "code expired" (each a distinct error message) from a genuine wrong-digits mismatch, and matters because attempts must **not** be incremented against a dead (used/expired) code. On a real digit mismatch it calls `incrementAuthCodeAttempts`; if that reaches 5 it kills the code with `expireAuthCode` — **not** `markAuthCodeUsed`, since a code burned by wrong guesses was never redeemed, and stamping `used_at` would make this endpoint's own already-used branch tell the user their code was "already used" when they never entered it correctly. On match it calls `markAuthCodeUsed` and **checks the return value**: `undefined` means a concurrent request carrying the same correct code already consumed it, and this one returns the already-used error instead of minting a second session. Then it generates an opaque 32-byte session token (`randomBytes(32).toString('hex')`), stores only its SHA-256 hash (via `hashSessionToken` in `sessions-store.ts` — deliberately a separate function from `hashAuthCode` despite the identical body, because the two hash different secrets with different threat models and keying one must not silently key the other) via `createSession`, and sets the raw token as the `session` cookie with `httpOnly`, `secure`, `sameSite: 'lax'` — mirrors the code-hashing pattern (raw value never persisted, only its hash). Any future code-comparison endpoint should use `timingSafeEqual` on equal-length hash buffers (see `hashesMatch` in that file) rather than `===`, to avoid a timing side-channel.
- `src/routes/login/+page.svelte` (US-B04) is the whole login flow in one page: a single "Send me a code" button that `POST`s to `/api/auth/request-code`, then an in-place transition (`step` state, not a second route) to a 6-digit code field that `POST`s to `/api/auth/verify-code` and `goto`s `/inbox`. **No email input field may ever appear here** — the recipient is the server-side `AUTH_RECIPIENT_EMAIL` constant (FR-1). Four conventions in it worth reusing:
  - The code field normalizes in `oninput` (`value.replace(/\D/g, '')`), not via a `pattern` attribute. `pattern` is inert on any form whose `onsubmit` calls `preventDefault()` and fetches manually — native constraint validation never runs. This also handles the `123 456`/`123-456` shapes people paste out of an email client.
  - The `role="alert"` error `<p>` is wrapped in `{#key errorNonce}`, with the nonce bumped every time an error is set. A live region whose new text is byte-identical to its old text is **not** re-announced, so two identical consecutive failures would otherwise be announced once. Do this for any repeated-error live region, not just this page.
  - `errorMessage` clears on input, so a stale failure doesn't sit on screen while the user is mid-correction.
  - It auto-submits once six digits are present (autofill delivers all six at once).
- There is deliberately **no `429` handling in the verify-code client path**: `/api/auth/verify-code` is not rate-limited — every rejection is a `400`. Brute force is bounded by the two limits that do exist (5 attempts per code, 3 codes per 10 minutes = at most 15 guesses per 10 minutes against a 10^6 space). If you find yourself writing a 429 branch there, add the server-side limit first or leave it out; a dead client branch for an impossible response is how the UI and server drift apart.
- A **real Resend API key is provisioned** in the local `.env` as of US-B04 — clicking "Send me a code" against a local dev server sends a real email to `AUTH_RECIPIENT_EMAIL`. Stub `/api/auth/request-code` in-page (`window.fetch`) when browser-testing steps that only need to reach the code-entry screen, and seed a known code hash directly into `auth_codes` instead.
- **All env vars are real and current in both the local `.env` and Vercel project settings** as of US-E01 (Turso, R2, Resend API key + recipient, and the inbound webhook secret). There are no placeholder credentials left in this project, and no outstanding credential-provisioning steps — if a future story hits an auth/credential failure, treat it as a real bug rather than assuming a stub value. `.env.example` documents every required name with empty values; the real ones live only in the gitignored `.env`.

## Design tokens (Dusk Terminal)

- All Dusk Terminal tokens (palette, fonts, radius scale, motion) live in `src/routes/layout.css`, using Tailwind v4's CSS-first `@theme` config — there is no `tailwind.config.js`/`.ts`.
- Palette: raw hex values are plain custom properties named `--dt-*` (e.g. `--dt-background`) set in `:root` (dark, the reference theme), overridden inside a `@media (prefers-color-scheme: light)` block scoped to `:root:not([data-theme])` (OS-default fallback), and again in `:root[data-theme='dark']` / `:root[data-theme='light']` (explicit user choice, always wins). The `@theme` block then maps Tailwind's color namespace onto these (`--color-background: var(--dt-background)`, etc.) so utilities like `bg-background`, `text-text-primary`, `border-border`, `text-accent`, `text-danger` are generated and theme-switch automatically. **Do not** set `--color-background: var(--color-background)` (self-reference) inside `@theme` — Tailwind's theme keys and the raw per-theme variables must have different names (`--dt-*` vs `--color-*`), or the custom property becomes CSS-invalid.
- Fonts: `@fontsource/inter` and `@fontsource/jetbrains-mono` are installed as real npm dependencies and imported directly in `layout.css` (`@import '@fontsource/inter/400.css';` etc., only the weights actually used: 400/500/600/700 for Inter, 400/500 for JetBrains Mono) — self-hosted, no external font CDN request at runtime. Exposed as `font-sans` (Inter) and `font-mono` (JetBrains Mono) Tailwind utilities. Per `tasks/prd-ui-ux.md` FR-2, monospace must be used for all metadata (timestamps, addresses, thread/message ids, the login code field), sans for everything else.
- Radius: the entire Tailwind radius namespace (`--radius-xs` through `--radius-full`, including `DEFAULT`/`--radius`) is overridden in `@theme` to values in the 2-4px range — this intentionally makes `rounded-full` non-pill-shaped in this app, matching the "no pill shapes, 2-4px everywhere" design rule. Don't add a new radius utility outside this scale.
- Motion: `--duration-fast` (120ms) / `--duration` (140ms) / `--duration-slow` (160ms) and `--ease-standard` (`cubic-bezier(0, 0, 0.2, 1)`, standard ease-out) are theme vars too, giving `duration-fast`/`duration`/`duration-slow` and `ease-standard` Tailwind utilities for all transitions. No bounce/spring easing per the design system.
- Theme toggle logic (not just CSS) lives in `src/lib/theme.svelte.ts`: `themeState` (a `$state` rune) tracks the explicit user choice (`'dark' | 'light' | null`, `null` = follow OS), `applyTheme`/`toggleTheme` set/clear the `data-theme` attribute on `<html>` and persist to `localStorage` (`dusk-terminal-theme` key). Call `initTheme()` once from the root `+layout.svelte` to sync `themeState` with `localStorage` on mount. `src/app.html` has a small inline (pre-hydration) script that reads the same `localStorage` key and sets `data-theme` before first paint, to avoid a flash of the wrong theme — keep that script and the `theme.svelte.ts` logic using the exact same storage key and value shape if either changes.
- `src/lib/components/ThemeToggle.svelte` is the reusable toggle button; `src/routes/dev/tokens/+page.svelte` is a dev-only page (unauthenticated, outside the `(app)` route group) that renders every token as a swatch/sample for visual QA — not part of the real app shell (that's US-J02), just a verification aid. Reuse this page rather than building a new one when adding future tokens.

## App shell

- `src/routes/(app)/+layout.svelte` is the real app shell (US-J02): a top bar (app mark, search input, `POST /api/auth/logout` form) above a flexible pane rendering `{@render children()}`, with no horizontal scroll down to 375px. US-J02 also gave it a fixed `w-[360px]` left column (`hidden lg:flex`) as a placeholder for the thread list; **US-F01 removed that column** — a thread list belongs to the inbox subtree, not to every `(app)` route (`/contacts` in US-I01 would have inherited one beside it). If the list/detail split is ever built, it belongs in `inbox/+layout.svelte` rather than back in the shell — US-G01 deliberately deferred it (see the thread-view section).
- **Any internal `<a href="/...">` (or programmatic navigation) must wrap the path in `resolve(...)` from `$app/paths`** (e.g. `href={resolve('/inbox')}`), not a raw string — this kit version's `svelte/no-navigation-without-resolve` lint rule fails `npm run lint` otherwise. Apply this to every new internal link across the app, not just the shell.

## Shared components

- `src/lib/components/` is the home for shared, feature-agnostic UI components — `ThemeToggle.svelte` (US-J01), and `EmptyState.svelte` / `Skeleton.svelte` / `ErrorMessage.svelte` (US-J03, implementing the design system's Empty/Loading/Error rules from `tasks/prd-ui-ux.md`). Feature-specific components should live under their own route/feature folders instead; only put something here if more than one feature will use it.
- `EmptyState` takes `message` (required) + optional `subCopy`; `Skeleton` takes `rows` (default 3) and renders that many pulsing `bg-surface` rows; `ErrorMessage` takes `message` (required) + optional `onRetry` and renders in `text-danger`, showing a Retry button only when `onRetry` is passed. All three are demoed on `/dev/tokens` under "Shared states" — extend that section (don't build a parallel demo page) when adding more shared components.
- Accessibility contract for these three: `Skeleton`'s pulse uses `motion-safe:animate-pulse` so it stops under `prefers-reduced-motion` (use `motion-safe:` for any future indefinite animation, not bare `animate-*`). `Skeleton` carries `role="status" aria-label="Loading"` itself, but **the consumer** is responsible for putting `aria-busy="true"` on the container whose content the skeleton is standing in for, and dropping it when real content arrives — do that in every consuming story (US-F01, US-G01, US-H01, US-I01) rather than inventing a per-caller convention. In `ErrorMessage`, `role="alert"` sits on the inner message `<span>`, not the flex wrapper, so the Retry button isn't read out as part of the alert announcement — keep live-region roles on the text node when a control sits beside it.
- When demoing/QAing a `bg-surface`-toned component (like `Skeleton`), wrap it in a `bg-background` container, not another `bg-surface` — same-tone nesting makes it visually disappear. Real usage in an actual list won't have this problem since the page background provides the contrast.

## Workflow

- This repo follows the Ralph per-story branch + PR workflow described in `agents/ralph.md`, driven by `agents/prd.json`. One story per branch/PR; the agent opens the PR, runs `/code-review` on it, fixes findings and re-reviews until a pass is clean, then squash-merges to `main` itself.
- **One story per session.** After a merge, the next story starts in a fresh session (`/clear`), so each story is implemented by an agent whose context is `main` + the docs rather than the accumulated transcript of earlier stories. That's what makes `agents/ralph.md`, `agents/progress.txt` and this file the actual handoff — anything a later story needs to know has to be written down in one of them before the merge, not left in conversation.
